# Урок 11. JSON и контракты данных

Предварительно нужны классы и свойства, массивы и списки, исключения, `using` и работа с текстовыми файлами из уроков 8–10. После урока вы сможете сохранять данные приложения, проверять прочитанное и объяснять, почему корректный JSON ещё не означает корректный заказ. Весь код использует `System.Text.Json` из .NET; устанавливать пакет не требуется. Имена в файле принадлежат внешнему контракту, а имена в программе — модели. Между ними должно существовать явно выбранное соответствие.

## 1. Что именно сохраняется

Объект живёт в памяти программы, содержит значения и ссылки, а иногда методы и события. JSON хранит текстовое представление данных: объекты с именованными свойствами, массивы, строки, числа, логические значения и `null`. Сам JSON не хранит тип вашего класса, адрес объекта или реализацию метода. Десериализация создаёт новый объект и заполняет его по правилам выбранного типа. Поэтому сохранение объекта и копирование произвольного графа объектов — разные задачи.

Сериализация преобразует значение в JSON; десериализация выполняет обратное преобразование согласно модели. Например, массив чисел становится JSON-массивом, а объект с публичными свойствами — объектом JSON. Формат имени свойства важен: `Name` и `name` являются разными именами. Пробелы и переносы между элементами обычно не меняют смысл документа. Пробел внутри строкового значения, напротив, является данными.

Сначала решайте, какие данные действительно должны пережить перезапуск. Счётчик просмотров может быть частью состояния, а открытый файловый поток, обработчик события или пароль для отладки — нет. Удобно выделять простые модели передачи данных: DTO, то есть объекты, чья задача описывать сохраняемые значения. Это не особое ключевое слово C#, а роль класса. Даже маленькому приложению полезна такая граница: она не даёт случайно сохранить лишние подробности внутренней реализации.

## 2. Свойства, поля и первое преобразование

Подготовим модель и выполним оба направления:

```csharp
var card = new Card { Name = "Книга", Count = 2 };
string json = JsonSerializer.Serialize(card);
Card? restored = JsonSerializer.Deserialize<Card>(json);

public sealed class Card
{
    public string Name { get; set; } = "";
    public int Count { get; set; }
}
```

Перед этим нужен `using System.Text.Json;`. Запись `<Card>` сообщает сериализатору целевой тип. Это готовое использование обобщённого метода; собственные обобщённые методы подробно появятся в следующем уроке. Здесь достаточно понимать, что указанная модель определяет ожидаемые свойства и типы значений.

В стандартной конфигурации участвуют публичные свойства, а обычные поля исключены. Замена `public int Count;` на свойство с `get; set;` способна исправить потерю данных без изменения файла. Опция `IncludeFields` существует, но включать её вместо понимания модели не следует. Стандартное сопоставление имён чувствительно к регистру. Поэтому чтение `{"count":2}` в модель с `Count` может оставить значение по умолчанию. Отдельно проверяйте, что реально прочиталось, а не только отсутствие исключения.

Инициализатор свойства сохраняется, если соответствующее поле JSON отсутствует и обычные правила модели допускают пропуск. Это удобно для необязательных настроек, но опасно для обязательного идентификатора. Число `0` после чтения само по себе не говорит, был ли ключ передан.

## 3. Настройки сериализатора и строковые данные

Объект `JsonSerializerOptions` задаёт конкретную политику преобразования. `WriteIndented = true` добавляет отступы и делает файл удобным для чтения. `PropertyNamingPolicy = JsonNamingPolicy.CamelCase` задаёт имена при записи и соответствующий контракт модели. `PropertyNameCaseInsensitive = true` отдельно разрешает нечувствительное к регистру сопоставление при чтении. Это разные настройки: одну нельзя мысленно подменять другой.

Не собирайте JSON конкатенацией кавычек. Текст пользователя может содержать перенос строки, обратную косую черту и кавычку. Сериализатор корректно экранирует эти символы. После обратного чтения должна получаться исходная строка, даже если её видимое представление в JSON содержит последовательности с обратной косой чертой. Разные допустимые способы записи Unicode не делают документы разными по смыслу.

Если структуру нужно строить непосредственно при записи, используйте `Utf8JsonWriter`. Для объекта последовательность вызовов выглядит как `WriteStartObject`, `WriteString` для текстового свойства и `WriteEndObject`. Writer самостоятельно экранирует строку; после `Flush` байты MemoryStream можно декодировать как UTF-8. Это более низкий уровень, чем сериализация готового DTO: вы явно управляете границами объекта и именами свойств, сохраняя корректность строкового формата. Writer и буфер освобождаются через using.

Для точного round trip задайте границу Unicode. Строка C# состоит из кодовых единиц UTF-16 и технически может содержать непарный суррогат. Writer способен заменить такой некорректный фрагмент символом U+FFFD, поэтому обещание сохранить любую возможную строку C# было бы неверным. В упражнении допускается только корректная последовательность: старший суррогат сразу перед младшим, без одиночных суррогатов. Emoji вне базовой плоскости представлены корректной парой и сохраняются. Валидация проходит строку до записи, отклоняя неверные пары через ArgumentException; символы управления и пустая строка по-прежнему допустимы.

Стандартное перечисление записывается числом. Если внешний формат требует строковое имя, подключают `JsonStringEnumConverter`. Настройка `allowIntegerValues: false` запрещает числовое представление, но ещё не задаёт точный набор допустимых строк: конвертер способен принять пробелы или комбинацию имён. Если договор разрешает только Pending и Done без внутренних пробелов по OrdinalIgnoreCase, читайте JSON-строку через DOM и явно сравнивайте её декодированное значение с этими двумя именами. Не применяйте Trim: он расширил бы язык входа. При записи проверяйте, что значение определено в enum: приведение `(Status)99` компилируется, хотя такого состояния нет в объявлении. Проверенное значение сериализуется в каноническое имя строковым конвертером.

Не меняйте общие опции случайно в середине программы. Согласованный набор настроек должен использоваться при обеих сторонах преобразования. Иначе один метод пишет формат, который другой интерпретирует иначе. Для учебных задач отдельная фабрика опций делает правило видимым и легко проверяемым.

## 4. Синтаксис, типы и предметные ограничения

Есть несколько независимых уровней проверки. Непарная скобка означает синтаксическую ошибку. Строка вместо ожидаемого числа нарушает контракт типа. Отрицательное количество товара может быть полностью корректным JSON-числом и допустимым `int`, но нарушает правило приложения. Поэтому десериализацию обычно сопровождает доменная валидация:

```csharp
var card = JsonSerializer.Deserialize<Card>(json);
if (card is null || string.IsNullOrWhiteSpace(card.Name) || card.Count < 0)
    throw new JsonException("Некорректная карточка.");
```

Nullable-результат здесь честно отражает возможность JSON-корня `null`. Оператор `!` только отключает предупреждение компилятора, он не добавляет выполнение проверки. То же относится к вложенным моделям: непустой заказ может содержать `null` вместо массива, а массив — `null` вместо строки заказа. Проверяйте каждый уровень, прежде чем обращаться к его членам.

Числовая граница тоже часть договора. Для цены обычно подходит `decimal`, для координаты — `double` с проверкой конечности и диапазона. Большая JSON-экспонента может не представляться конечным `double`. Не полагайтесь на успешное чтение числа как на доказательство его пригодности. Политика ошибок должна быть явной: неверный аргумент метода, порча внешнего документа и отказ файловой системы имеют разные причины и не обязаны скрываться одним `catch`.

## 5. DOM и три состояния свойства

Когда структура невелика или зависит от версии, удобен `JsonDocument`. Его `RootElement` позволяет исследовать дерево без объявления полного набора DTO. Документ владеет внутренней памятью и освобождается через `using`. Нельзя вернуть наружу зависимый `JsonElement`, затем уничтожить документ и ожидать безопасной работы элемента; можно извлечь самостоятельные числа и строки либо явно клонировать элемент.

Для свойства различайте отсутствие, JSON `null` и конкретное значение. Например, в частичном обновлении профиля отсутствие `bio` означает «сохрани старое», `"bio":null` — «сбрось», строка — «замени». Обычная nullable DTO без дополнительного признака наличия может смешать первые два случая.

Алгоритм чтения DOM начинается с `ValueKind`: сначала ожидаемый тип корня, затем `TryGetProperty`, затем тип найденного значения и только потом `GetString` или `TryGetInt32`. Это даёт контролируемую диагностическую ошибку вместо случайного `InvalidOperationException`. `TryGetProperty` сообщает наличие ключа, а не корректность его значения.

JSON допускает неоднозначные для приложения ситуации, включая повтор имени свойства. Если договор требует уникальности ключей обновления, обойдите `EnumerateObject()` и ведите `HashSet<string>`. Не оставляйте выбор первой или последней записи неявным. Точное правило особенно важно там, где документ меняет уже существующее состояние.

## 6. Файлы, версии и безопасный импорт

Для маленького файла допустим путь `ReadAllText` → `Deserialize`, а сохранение выполняется через `Serialize` → `WriteAllText`. Все ошибки доступа и устройства продолжают иметь значение. Отсутствующий файл можно трактовать как первый запуск, если это явно предусмотрено. Повреждённый существующий файл не стоит автоматически считать первым запуском: пользователь потеряет настройки и не узнает причину.

Формат со временем меняется. Поле `version` позволяет сначала выбрать схему, затем преобразовать её во внутреннюю модель. У старой версии может быть `label`, у новой — `name` и обязательное число повторов. Значение по умолчанию для старого формата является правилом миграции. Оно не разрешает молча принимать пропущенное обязательное поле новой версии. Неподдержанную будущую версию лучше явно отклонить, чем угадать её значение.

При импорте целого каталога готовьте новое состояние отдельно. Сначала прочитайте весь массив, проверьте элементы, диапазоны и уникальность ключей. После успешной проверки выполните одно присваивание. Тогда ошибка в последнем элементе не разрушит прежний каталог. Это защита состояния в памяти, но ещё не гарантия атомарного сохранения на диск при отключении питания.

Построчный NDJSON устроен иначе: каждая строка — независимый документ. Здесь разумна другая политика: записать номер ошибочной строки и продолжить. Номер должен учитывать и пропущенные пустые строки. Не смешивайте эти два режима импорта: требования к целостности определяет задача, а не выбранный API.

## 7. Как проверять и отлаживать

Начинайте с самого короткого документа, в котором заметно расхождение. Проверьте имя свойства, регистр, наличие `get/set`, фактический `ValueKind` и настройки вызова. Если число осталось нулём, сравните случаи «ключ отсутствует» и «ключ явно равен нулю». Если объект равен `null`, выясните, был ли корень JSON `null`, вместо немедленного добавления `!`.

Проверка round trip сравнивает смысл данных, а не обязательно текст. Для объекта допустим другой порядок свойств, для строки — другая форма экранирования. Для массива порядок обычно значим. Вход `[3,-1,3,0]` полезнее отсортированного: он обнаружит случайную сортировку и удаление повторов. Проверяйте независимо пустой массив, отсутствующие поля, неправильные типы и доменные границы.

Файловые тесты создают уникальный временный каталог и удаляют его в `finally`. Они не читают реальные пользовательские документы. После неуспешного импорта сравните прежний экспорт с новым: одного Count недостаточно, потому что могли поменяться записи при том же количестве. Тест должен проваливаться на реалистичной ошибке, а не просто повторять название сценария в консоль.

## 8. Самопроверка и развёрнутые ответы

Сначала ответьте самостоятельно: почему поле не восстановилось; чем отсутствие свойства отличается от `null`; когда допустимо вернуть настройки по умолчанию; что проверять при round trip; почему импорт нельзя начинать с `Clear`.

Ответ 1. Стандартный контракт исключает обычные поля. Проверьте модель и сделайте предназначенное для хранения значение публичным свойством либо осознанно выберите другую конфигурацию. Смена регистра JSON отдельно не исправляет исключённое поле.

Ответ 2. Отсутствие означает, что документ ничего не сообщил о данном свойстве. `null` является переданным значением. В patch эти состояния часто означают сохранение старого значения и его сброс соответственно. Для различения нужен признак наличия, например `TryGetProperty`.

Ответ 3. Дефолт уместен в заранее определённой ситуации, например при первом запуске без файла. Отказ доступа, испорченный синтаксис и неверный диапазон не превращаются в отсутствие файла. Их следует диагностировать согласно контракту приложения.

Ответ 4. Сравнивайте значения свойств, точный порядок и повторы массива, а при ссылочных моделях не путайте новую ссылку с ошибкой. Для строки с кавычками и переносом обратное чтение должно вернуть исходные символы. Это сильнее сравнения только длины JSON.

Ответ 5. `Clear` меняет рабочее состояние до подтверждения корректности нового. Ошибка в последней записи оставит пустой или частичный каталог. Временный проверенный снимок и последующая замена сохраняют старое состояние при неуспехе.

Официальная справка для сверки поведения: [десериализация System.Text.Json](https://learn.microsoft.com/en-us/dotnet/standard/serialization/system-text-json/deserialization). В задачнике остаются отдельные условия; подробные разборы и исполняемые проверки расположены в решениях этого урока.
