# Модуль 10. Исключения, ресурсы и текстовые файлы

## 1. Три разных причины отсутствия результата

Нужны методы, nullable-строки, коллекции, классы и интерфейсы. Здесь мы добавляем работу с внешним ресурсом и учимся различать нормальное отсутствие, неверные данные и отказ операции. Сначала запустите [пример](examples/Program.cs), затем решайте [условия](TASKS.md). [Разборы](SOLUTIONS.md) показывают точные типы ошибок и состояние после каждого отказа. JSON и асинхронность в этом модуле пока не требуются.

Операция чтения может закончиться без следующей строки: это EOF, конец потока. Строка может существовать, но содержать `wrong` вместо числа: это ошибка данных. Наконец, источник может перестать читаться: это ошибка канала ввода-вывода. Возврат нуля на все три случая уничтожает информацию и делает корректный ноль неотличимым от неудачи.

Сначала определите контракт метода. Возвращает ли он nullable-результат при отсутствии? Сообщает ли ожидаемый отказ через Try-метод? Бросает ли исключение при невозможности выполнить обязательную операцию? Любой из вариантов может быть уместен, но смешивать их без правил нельзя. Например, необязательный файл может отсутствовать, а обязательный порт должен быть действительно прочитан.

В файловых заданиях весь эксперимент проводится в собственном уникальном временном каталоге. Мы не читаем личные документы и не меняем пользовательские настройки. Это даёт повторяемые входы и понятное владение: тест создал данные, проверил результат и удалил только созданную им папку. Такой подход также позволяет честно проверить ошибку, не ломая реальную среду.

## 2. Throw, catch и сохранение причины

Исключение прерывает обычный ход выполнения и ищет подходящий обработчик по стеку вызовов. `throw new FormatException(...)` создаёт и бросает объект ошибки. `catch (FormatException error)` принимает подходящее исключение и даёт доступ к описанию. Если нужного обработчика нет, ошибка выходит выше; это предпочтительнее выдуманного успешного результата.

```csharp
static int ReadPort(TextReader reader)
{
    string line = reader.ReadLine()
        ?? throw new EndOfStreamException("Ожидалась строка порта.");
    int port = int.Parse(line, System.Globalization.CultureInfo.InvariantCulture);
    if (port < 1 || port > 65535)
        throw new ArgumentOutOfRangeException(nameof(port));
    return port;
}
```

EOF, неверная запись, переполнение int и порт вне разрешённого диапазона здесь различимы. `int.Parse` проверяет синтаксис и вместимость int; наша дополнительная проверка задаёт диапазон порта. `nameof` получает имя символа для диагностики, не выполняя вычисления значения. В тесте проверяется конкретный тип отказа, а не только факт «что-то пошло не так».

Порядок обработчиков имеет значение из-за наследования. FileNotFoundException является частным случаем IOException, а IOException — частным случаем Exception. Поэтому частный catch должен идти перед более общим. Общий Exception перед IOException делает второй обработчик недостижимым, что компилятор обнаруживает. Но просто переставить их бывает недостаточно: чрезмерный общий catch всё равно маскирует неожиданные дефекты.

Если ошибка преобразуется в доменную, сохраняйте оригинальную причину через `InnerException`. Пользователю сервиса настроек полезно сообщение «не удалось прочитать настройки», а диагностике нужна исходная IOException. Создание нового исключения только с прежним Message теряет связь между уровнями. Оборачивать нужно лишь оговорённые типы; ошибка формата не обязана превращаться в ошибку канала.

Если внутри catch требуется передать ту же ошибку выше без оборачивания, используется `throw;`. Запись `throw error;` заново бросает переменную и влияет на сведения о месте повторного броска. В учебных тестовых reader заранее созданное исключение намеренно служит входными данными; в обычном обработчике повторный бросок выбирают осознанно.

## 3. Finally, IDisposable и using

Ресурс может требовать своевременного завершения работы: файловый дескриптор нужно закрыть, буфер записи — сбросить. Сборщик мусора управляет памятью объектов, но не задаёт удобный момент освобождения каждого внешнего ресурса. Интерфейс IDisposable предоставляет Dispose как явную границу окончания использования.

`finally` выполняется при выходе из соответствующего try как после успеха, так и при исключении. Он подходит для собственной очистки, которая нужна в обоих случаях. `using` строит такую границу для IDisposable и вызывает Dispose на выходе из области. Это гарантированное освобождение при обычных управляемых переходах, описанное в [справочнике Microsoft о using](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/statements/using).

```csharp
using (StreamReader reader = new(path, System.Text.Encoding.UTF8))
{
    string? line = reader.ReadLine();
    // Работа с reader только внутри области владения.
}
// Здесь reader уже освобождён.
```

Форма `using StreamReader reader = ...;` освобождает ресурс в конце текущей области. Если запись должна закончиться до последующего чтения файла, удобнее явный блок: он делает нужную границу заметной. Не рассчитывайте, что один вызов WriteLine уже завершил работу всех буферов и освободил файл.

При исключении внутри using Dispose выполняется до внешнего catch. Поэтому журнал действий имеет порядок `body, dispose, catch, finally`. Строки после неудачного тела пропускаются. В тесте полезно сравнить весь журнал, поскольку одна проверка счётчика освобождений не обнаружит неверный порядок относительно обработчика.

Хорошая учебная реализация Dispose идемпотентна: повторный вызов не освобождает ресурс второй раз. Флаг disposed помогает отклонить последующее использование через ObjectDisposedException. Но не каждый класс обязан иметь Dispose. Добавлять его к обычной модели кошелька только ради модного шаблона не нужно; нужна реальная обязанность завершить использование ресурса.

## 4. Кто владеет TextReader и как читать до EOF

TextReader задаёт общую возможность читать символы и строки. StreamReader читает поток или файл с декодированием, StringReader читает готовую строку в памяти. Благодаря общему типу алгоритм разбора тестируется без настоящего файла. Для проверки отказа можно создать маленький reader, детерминированно бросающий указанную IOException.

Метод, получивший reader от вызывающего, обычно не получает автоматически право его закрыть. В наших условиях владение указано прямо: переданный reader остаётся у вызывающего, а созданный внутри метода reader освобождает сам метод. Правило должно быть одинаковым и на успешном пути, и при ошибке. Неожиданный Dispose может сломать последующее чтение хвоста.

```csharp
string? line;
while ((line = reader.ReadLine()) is not null)
{
    if (string.IsNullOrWhiteSpace(line)) continue;
    // Обработка содержательной строки.
}
```

ReadLine возвращает строку без завершающего перевода строки. Пустая строка — настоящий прочитанный результат, а null означает отсутствие следующей строки. Если остановиться на `line == ""`, документ с пустой строкой посередине будет обрезан. Завершающий перевод строки и отсутствие последнего перевода не должны случайно менять смысл числовых записей.

Потоковый алгоритм держит одну строку вместо всего документа. Для поиска первой длинной строки он также позволяет остановиться немедленно, оставив остальной текст вызывающему. Тест может после метода прочитать следующую строку: это одновременно проверяет ранний выход и сохранение владения. Указанный в условии Length измеряет UTF-16 code units, а не число видимых символов; emoji может занимать две такие единицы.

ReadToEnd уместен, когда результатом нужен весь текст и размер ограничен. Он неудобен, когда нужна только первая подходящая строка или документ потенциально большой. Выбор определяется результатом и ограничениями памяти, а не тем, какой метод короче написать.

## 5. Пути, кодировка и границы записи

Path.Combine соединяет компоненты пути, учитывая платформенные правила. Это лучше ручного добавления слеша, но не является проверкой безопасности или допустимости имени. Абсолютный второй компонент и переход `..` могут изменить смысл пути. Если задача разрешает только одно имя, проверяйте именно один компонент, а не произвольную строку пути.

В учебном ResolveChild разрешён небольшой набор ASCII символов и отдельно запрещены `.` и `..`. Это синтаксический контракт, а не полная модель всех ограничений операционной системы. Например, специальные имена устройств и символические ссылки требуют отдельной политики, если программа действительно должна создавать произвольные внешние файлы. Наш тест не создаёт файлов по спорным именам и не обещает полноценную песочницу.

Текст в памяти и байты файла различаются. UTF-8 кодирует кириллицу и emoji без привязки к локальной кодовой странице. `new UTF8Encoding(false, true)` задаёт отсутствие записываемого BOM и строгую обработку некорректных последовательностей. Число байтов не равно числу символов строки. Для известного слова полезен тест точных байтов, дополняющий обычное сравнение текста.

BOM — начальная последовательность байтов, обозначающая кодировку. Если контракт допускает только UTF-8, автоматическое распознавание всех BOM может принять лишнюю кодировку. В строгой задаче мы читаем байты, убираем только UTF-8 префикс `EF BB BF` и декодируем строго. Повреждённые `C3 28` должны вызвать DecoderFallbackException, а не незаметно превратиться в символ замены.

Режим записи также является частью контракта. Обычная перезапись заменяет прежнее содержимое, append дописывает в конец. В журнале каждая запись занимает одну строку, поэтому внутри сообщения запрещены CR/LF, но пустое сообщение допустимо. После всех using файл читается; пустая запись должна сохраниться как пустая строка, а не исчезнуть при дополнительной фильтрации.

WriteAllText сохраняет переданные переводы строк, тогда как пересборка через WriteLine использует выбранный перевод строк writer. Поэтому задача точного round-trip и задача журнала отличаются. В первой сравнивают всю строку с CRLF и LF, во второй — последовательность логических записей.

## 6. Восстановление ошибок и подготовка перед фиксацией

Для ожидаемых плохих чисел удобен TryParse. Он сообщает неуспех без выбрасывания ошибки формата и позволяет продолжить следующую строку. При этом физический номер строки увеличивают до пропуска пустых строк. Иначе сообщение «ошибка в строке 3» начнёт указывать на третье число, а не на реальную третью строку документа.

Ошибка данных относится к одной записи; ошибка чтения относится к источнику. Нельзя catch всех исключений вокруг цикла и объявлять их одной невалидной строкой: канал мог перестать отдавать данные совсем. В задачах импорта восстановление после плохой записи предусмотрено, а IOException проходит наружу. Такая граница сохраняет честность отчёта.

Необязательный файл показывает другую стратегию: только FileNotFoundException и DirectoryNotFoundException превращаются в null. Пустой существующий файл остаётся пустой строкой. Предварительный File.Exists не заменяет обработку ReadAllText, потому что состояние может измениться между проверкой и действием. Ошибка аргумента не является отсутствием файла и не должна подавляться.

Чтобы не менять старый файл до готовности нового содержимого, можно писать в уникальный staging рядом с целью. После успешной подготовки выполняется операция замены. В учебной задаче имитированная IOException бросается до этой точки: старый файл обязан сохраниться, staging должен исчезнуть в finally. Успешный сценарий подтверждает новое содержимое и отсутствие лишних файлов.

Эта проверка доказывает только заявленную границу отказа до фиксации. Она не доказывает сохранность при отключении питания, отказе накопителя или всех файловых системах. Такие свойства требуют иных механизмов и испытаний. Полезно точно назвать проверенный сценарий вместо общего утверждения «запись теперь абсолютно безопасна».

## 7. Детерминированная проверка и вопросы

При обработке нескольких файлов не полагайтесь на порядок перечисления каталога. Отсортируйте имена по явно указанному правилу. Если расширение должно быть в точности `.txt`, используйте явное Ordinal-сравнение, иначе особенности маски и регистра могут дать различия между системами. Для суммы int из многих файлов используйте long, а для ошибок сохраняйте имя и физический номер строки.

Создавайте тестовую папку с GUID под Path.GetTempPath, а файлы — только внутри неё. Область try/finally должна охватывать операции с созданным содержимым. После освобождения всех reader и writer удаляйте собственную папку. В тестах отказа используйте заданные исключения и байты, а не сетевые отключения, ожидания времени или нестабильные права доступа.

Проверяйте успех и отказ отдельно. Для строгого декодера корректная кириллица не доказывает отказ на повреждении. Для записи через staging новая строка не доказывает сохранность старой при исключении. Для using нормальный выход не заменяет выход с ошибкой. Для читателя требуется тест EOF и отдельный тест пустой строки посередине.

Самостоятельно ответьте: чем EOF отличается от пустой строки? Кто закрывает переданный TextReader? Почему общий catch стоит последним и часто вообще не нужен? Что теряется при создании исключения только с Message? Почему мягкий UTF-8 декодер может пройти тест кириллицы и всё же нарушать контракт? Какой результат должна вернуть функция для отсутствующего и пустого необязательного файла?

## 8. Ответы самопроверки

**EOF и пустая строка.** Null означает, что следующей строки нет. Пустая строка означает прочитанную строку между переводами строк или перед ними. Цикл должен продолжаться после неё. Проверка whitespace определяет полезность содержимого, но не наличие следующей строки. Физическая нумерация учитывает также пропущенные пустые строки.

**Владение reader.** Переданный reader в наших контрактах остаётся у вызывающего. Метод использует его и возвращает результат, не вызывая Dispose. Если метод сам открыл StreamReader, он и завершает его использование через using. Именно поэтому тест чтения непрочитанного хвоста полезен: закрытый reader нарушил бы дальнейший сценарий.

**Порядок catch.** Обработчик базового исключения подходит также его наследникам. Более частный после общего недостижим. Общий catch не обязателен: часто корректнее перехватить только ожидаемое отсутствие файла, а ошибку аргумента или дефект реализации передать выше. Необработанное неожиданное исключение помогает найти проблему вместо ложного отчёта об успехе.

**Причина ошибки.** Один Message сохраняет только текст. InnerException сохраняет исходный объект с типом, сообщением и диагностической цепочкой. Обёртка добавляет контекст уровня приложения, не уничтожая причину. В тесте проверяется тождественность InnerException заранее созданной IOException, а не только похожая строка.

**Строгий UTF-8.** Корректный текст одинаково читают строгий и мягкий декодеры. Различающий вход должен содержать невалидную последовательность, например C3 28. Мягкий вариант выдаёт U+FFFD и продолжает, строгий бросает DecoderFallbackException. Оба сценария исполняются, поэтому тест замечает подмену политики обработки повреждений.

**Необязательный файл.** Отсутствие возвращает null, реальный пустой файл — строку нулевой длины. Это позволяет вызывающему отличить «настройки не заданы» от «настройки явно пустые». Остальные ошибки остаются ошибками. Если превратить всё в пустую строку, различие восстановить на следующем уровне уже невозможно.
