# Урок 12. Обобщённые типы и алгоритмы

Нужны коллекции, классы, интерфейсы, свойства, исключения и понимание ссылочных значений из предыдущих уроков. Здесь вы перейдёте от использования `List<int>` к написанию собственных методов и контейнеров с параметром типа. Цель — сохранять проверяемую типизацию и повторно использовать настоящий алгоритм. Обобщения не требуют превращать каждую функцию в универсальную: сначала определяют общую операцию, затем выясняют, какие сведения о типе ей нужны.

## 1. Тип как параметр

Методы `SwapInt` и `SwapString` выполняли бы одинаковые присваивания, различаясь типом переменных. Обобщённый метод выражает эту общую часть:

```csharp
static void Swap<T>(ref T first, ref T second)
{
    T saved = first;
    first = second;
    second = saved;
}
```

`T` — имя параметра типа. При вызове с двумя `int` компилятор выводит `T=int`; с двумя строками — `T=string`. Внутри метода `saved` имеет именно этот тип. В отличие от `object` не приходится делать обратное приведение и надеяться, что в переменной лежит ожидаемое значение. Ошибка несовместимых аргументов обнаруживается при компиляции вызова.

Обычный параметр `count` передаёт значение во время выполнения. Параметр `T` участвует в проверке типов и выборе подходящего варианта метода. Нельзя использовать тип так, будто он переменная с числом, или ожидать, что `T + T` допустимо для любого типа. Некоторым типам сложение вообще не определено. Универсальным остаётся только то, что разрешено при известных ограничениях.

Обмен ссылочными значениями переставляет ссылки и не копирует сами объекты. Передача `ref` нужна, чтобы изменить переменные вызывающего кода. При обычной передаче параметров перестановка затронула бы только локальные копии. Даже случай, когда обе `ref` ссылаются на одну переменную, полезен для понимания: временное сохранение не разрушает её значение.

## 2. Обобщённый класс и закрытый тип

В объявлении `class Box<T>` параметр относится ко всему классу. Его можно использовать в поле, свойстве, аргументах и возвращаемых значениях. Экземпляр `Box<int>` хранит числа; экземпляр `Box<string>` — строки. Это два разных закрытых типа, созданных из одного обобщённого определения.

Статические поля тоже принадлежат закрытому типу. Если у `Box<T>` есть `public static int Count`, то `Box<int>.Count` и `Box<string>.Count` независимы. Несколько экземпляров `Box<int>` разделяют первый счётчик, но не счётчик строкового типа. Создание нового экземпляра не сбрасывает static. При тестировании такого состояния делайте начальные условия явными, иначе результат будет зависеть от предыдущего запуска в том же процессе.

Параметров типа может быть несколько. В `Dictionary<TKey,TValue>` тип ключа и значения решает разные задачи. В собственном `MultiMap<TKey,TValue>` значение словаря может быть списком `TValue`, а параметр `TKey` определяет правило поиска группы. Хорошие имена объясняют роль, когда короткое `T` уже недостаточно выразительно.

Не сравнивайте разные закрытые типы как взаимозаменяемые только из-за общего определения. `List<int>` и `List<string>` имеют разный контракт. Обобщения дают общий исходный алгоритм, сохраняя точный тип данных на его границах. Это делает ошибки заметными раньше, чем набор взаимных приведений из `object`.

## 3. Default, nullable и явное наличие

`default(T)` означает начальное значение данного типа. Для `int` это ноль, для `bool` — false, для обычного ссылочного типа — null. Но ни одно из этих значений не является универсальным признаком отсутствия. Стек может действительно содержать ноль; успешный результат функции может действительно равняться null, если это допускает модель.

Поэтому контейнеры часто используют протокол Try:

```csharp
bool found = stack.TryPop(out int value);
if (found) Console.WriteLine(value);
```

Успех сообщает `bool`, а `out` переносит значение. Пустой стек возвращает false и назначает `default`; стек с сохранённым нулём возвращает true и тот же ноль. Это две разные ситуации с одинаковым значением второго канала.

В задачах встречается `default!`. Знак подавляет nullable-предупреждение в инфраструктурном месте, где значение не должно читаться при неуспехе. Он не проверяет инвариант во время выполнения. Если написать `Result<T>`, закрытый конструктор и проверяемое свойство `Value` должны не позволять читать отсутствующий результат. Фабрики `Ok` и `Fail` создают только согласованные состояния.

Nullable-аннотация также не заменяет проверку аргументов. Вызывающий код может подавить предупреждение через `!`, прийти из другой сборки либо нарушить контракт иным способом. Публичный метод, для которого требуется понятная ошибка null, выполняет настоящую проверку. Так статическая типизация и runtime-валидация дополняют друг друга.

## 4. Ограничения where

Без ограничений о `T` известно мало. Чтобы обращаться к `Key`, нужно доказать, что тип предоставляет это свойство:

```csharp
static T? Find<T>(IReadOnlyList<T> items, int key)
    where T : class, IHasKey
{
    foreach (var item in items)
        if (item.Key == key) return item;
    return null;
}

public interface IHasKey { int Key { get; } }
```

В рабочем методе добавляются оговорённые проверки null; фрагмент показывает только идею ограничения. `IHasKey` даёт доступ к `Key`, а `class` ограничивает типы ссылочными и позволяет возвращать null как отсутствие объекта. Ограничение описывает потребность алгоритма, а не конкретное имя класса.

`where T : IComparable<T>` даёт операцию `CompareTo`. Её знак сообщает относительный порядок; конкретное возвращаемое число не обязано быть ровно -1 или 1. Максимум ищут через `> 0`, равенство — через `== 0`. При выборе первого максимума замена выполняется только для строго большего значения. Замена на `>= 0` оставила бы последний объект среди равных.

`where TKey : notnull` удобно для ключей словаря. Оно помогает компилятору проверять типовые аргументы, но не является автоматической защитой всех вызовов от null. Ограничения должны быть минимальными: требовать создание `new T()` у алгоритма, который только сравнивает существующие элементы, излишне. Каждое дополнительное требование исключает часть полезных типов.

Если алгоритму действительно нужно создавать элементы, ограничение `where T : class, new()` обещает ссылочный тип и доступный публичный конструктор без параметров. `new T[count]` создаёт массив пустых ссылок, но не count объектов. Для независимых экземпляров нужен отдельный `new T()` на каждой итерации. Заполнение одной общей ссылкой имеет другой смысл; счётчик конструкторов и изменение одного элемента различают эти случаи.

## 5. Равенство, порядок и копирование

Равенство и упорядочивание — разные отношения. `IEqualityComparer<T>` определяет равенство и хеш-код для множества или словаря. `IComparable<T>` задаёт порядок. Для строк может понадобиться `StringComparer.OrdinalIgnoreCase`, чтобы ключи `A` и `a` считались одной группой, но исходное первое написание сохранилось в результате.

Алгоритм стабильного удаления повторов использует две структуры. `HashSet<T>` отвечает на вопрос о встреченном значении, а `List<T>` записывает первое появление в исходном порядке. Мы не полагаемся на порядок обхода самого множества. Так одинаковая формулировка результата остаётся верной при смене внутренней реализации контейнера.

Копирование массива `T[]` создаёт новые ячейки, но копирует хранимые значения. При ссылочном `T` это ссылки. Поэтому замена `copy[0]` не изменит `source[0]`, а изменение поля `copy[0].Value` может быть видно через исходный массив: оба указывают на один объект. Это поверхностная копия, и она часто именно то, что требуется.

Проверка только равенства элементов сразу после копирования не отличает копию от возврата исходного массива. Нужна проверка независимости структуры: заменить ячейку результата и наблюдать исходник. Универсальная глубокая копия потребовала бы правил для каждого вида объекта, обработки циклов и владения ресурсами. Обобщённый метод сам по себе этих сведений не имеет.

## 6. Контейнеры и их инварианты

До написания методов сформулируйте, что всегда должно оставаться верным. У стека элементы находятся в списке в порядке добавления, а снимается последний. У кольцевого буфера `Count` не превышает capacity, а `next` указывает на следующую ячейку записи. После полного заполнения эта же позиция соответствует старейшему сохранённому значению.

Кольцевой буфер не сдвигает массив при каждом добавлении. Индекс обновляется по модулю ёмкости. Снимок восстанавливает хронологический порядок отдельно: до заполнения начинает с нуля, после заполнения — с `next`. Тестировать только первый оборот недостаточно: ошибка порядка обычно проявляется после нескольких перезаписей. Ёмкость один — полезная граница, где запись всегда заменяет предыдущую.

В прямоугольной сетке один массив хранит элементы построчно. Линейный индекс равен `row * Columns + column`. Каждая координата проверяется отдельно. Проверка лишь линейного индекса пропустила бы `(0,Columns)` и ошибочно обратилась к первой ячейке следующего ряда. Прямоугольник с разными числами строк и столбцов обнаруживает ошибку формулы, незаметную на квадрате.

Выдача массива-снимка защищает внутреннюю структуру контейнера, но не делает хранимые ссылочные объекты неизменяемыми. Это нужно проговорить в контракте. Отдельно оценивайте стоимость: доступ по индексу обычно O(1), снимок O(n), двоичный поиск O(log n) сравнений только при отсортированном вводе и быстром индексаторе.

## 7. Почему List&lt;Cat&gt; не является List&lt;Animal&gt;

Каждая кошка является животным, но изменяемый список кошек нельзя безопасно считать изменяемым списком животных. Через `List<Animal>` можно было бы добавить собаку, и исходный `List<Cat>` оказался бы содержащим не кошку. Поэтому `List<T>` инвариантен: наследование типов элементов не создаёт такое присваивание списков.

Интерфейс чтения `IReadOnlyList<out T>` допускает ковариантность для ссылочных типов. Метод, который только читает `Animal`, способен безопасно получить объект `Cat`. Через этот интерфейс нельзя добавить произвольного `Animal` во внутренний список. Так функция чтения имён может принимать `IReadOnlyList<Animal>`, а вызывающий передавать `List<Cat>` без копии и приведений отдельных элементов.

Собственный `ISource<out T>` также только выдаёт значения: его метод `T Read()` возвращает T. Поэтому источник Dog можно безопасно использовать как источник Animal. Направление `ISink<in T>` противоположно: такой интерфейс только принимает T в `Write(T value)`. Приёмник любых Animal подходит там, где будут передавать лишь Dog. Это контравариантность: все переданные собаки допустимы для такого приёмника. Ключевые слова in/out объявляют разрешённое направление на интерфейсе, а не на конкретном вызове метода.

Типовая безопасность не задаёт протокол потребления сама. В задаче CopyAtMost источник предоставляет HasNext, а Read разрешён только после true и потребляет ровно один элемент. Приёмник успешно принимает каждое значение; EOF обрабатывается остановкой цикла, а не исключением. Проверка лимита перед чтением гарантирует, что limit=0 не потребляет данных. Помимо компиляции вариантных присваиваний, тесты проверяют реальные счётчики чтений и записей.

Слово ReadOnly описывает доступ через интерфейс, а не полную неподвижность объекта. Владелец исходного List по-прежнему может его менять. Если методу нужен стабильный снимок, он создаёт свою копию и явно платит временем и памятью. Аналогично readonly-поле запрещает замену ссылки после инициализации, но не делает сам список неизменяемым.

При диагностике generic-ошибки сначала прочитайте целевой тип целиком. Важны и внешний контейнер, и его параметры, и наличие разрешённой вариантности. Приведение через `object` способно отложить проблему до runtime, но не делает небезопасное отношение типов корректным.

## 8. Самопроверка и ответы

До чтения ответов объясните: как отличить пустой стек от сохранённого нуля; почему generic-метод не может вызвать произвольный `Key`; что копирует `Array.Copy`; почему двоичный поиск обязан получать отсортированный ввод; какой индекс старейшего элемента у полного кольца.

Ответ 1. Смотрите на bool из `TryPop`. При true значение действительно извлечено, даже если это ноль или null. При false контейнер пуст, а out-значение лишь назначено по контракту. Само значение не несёт признака наличия.

Ответ 2. Компилятор должен доказать существование свойства для всех допустимых T. Ограничение интерфейсом с `Key` предоставляет такое доказательство. Проверять тип вручную и приводить к нескольким конкретным классам означает отказаться от полезной общей границы.

Ответ 3. Копируются ячейки массива. Для ссылочного типа содержимое ячейки — ссылка, поэтому внешний массив независим, а внутренний объект может остаться общим. Проверки изменения ячейки и изменения объекта показывают разные уровни копии.

Ответ 4. Двоичный поиск отбрасывает половину кандидатов, опираясь на порядок. На несортированном вводе логическое основание исключения половины исчезает. Линейная проверка сортировки на каждом вызове также изменила бы заявленную общую сложность на O(n).

Ответ 5. После полного заполнения `next` указывает на ячейку, которую перезапишет следующее добавление, то есть на старейший элемент. До заполнения начало остаётся нулевым. Отсюда строится правильный порядок снимка.
