# Урок 16. Отладка, тестирование и структура приложения

## Что значит «программа работает»

Одного запуска на примере недостаточно. Программа может правильно обработать книгу с обычным названием,
но испортить файл после ошибки или повторно выдать удалённый ID. Поэтому сначала нужен наблюдаемый контракт:
какие данные допустимы, что возвращается, какие ошибки разрешены, какое состояние должно сохраниться.
Тест сравнивает наблюдаемое поведение с этим контрактом. Если ожидание взято из той же ошибочной формулы,
тест лишь повторяет реализацию и создаёт ложную уверенность.

В этом модуле мы соединяем изученные возможности C# в приложение из нескольких проектов.
Важно уметь объяснить не только успешный результат, но и то, почему проверка обнаружила бы правдоподобную ошибку.
Например, пустая очередь и стек имеют одинаковый Count=0 после полного опустошения.
Если проверять только количество, подмена одной структуры другой останется незамеченной.
Разные извлечённые значения делают порядок наблюдаемым.

## Проект, сборка и решение

Файл .csproj описывает один проект: целевую платформу, тип результата, ссылки и пакеты.
Библиотека содержит используемые другими проектами типы; консольный проект имеет точку входа.
Решение .slnx объединяет проекты для удобной сборки и открытия в IDE, но само не является программой.
Наличие проекта в решении не создаёт ссылку между его типами и другим проектом.

Ссылка ProjectReference означает, что проект использует код другого проекта и зависит от его сборки.
У итогового приложения консоль ссылается на ядро; тесты также ссылаются на ядро.
Ядро не ссылается ни на консоль, ни на тесты. Это направление защищает бизнес-правила от зависимости
от конкретного способа запуска. Если ядро начнёт читать Console.ReadLine самостоятельно,
проверять его без настоящего ввода станет труднее.

Общие TargetFramework, Nullable и TreatWarningsAsErrors находятся в Directory.Build.props.
global.json выбирает семейство SDK. Не следует исправлять отсутствие SDK случайной заменой платформы:
сначала выясните, какой инструмент реально выбран командой dotnet --info.

```powershell
dotnet restore "Курс CSharp.slnx" --locked-mode
dotnet build "Курс CSharp.slnx" -c Release --no-restore
dotnet test "capstone/Библиотека.Тесты/Библиотека.Тесты.csproj" -c Release --no-build
```

Restore получает зависимости, build проверяет исходники и создаёт сборки, test обнаруживает и выполняет тесты.
Флаг --no-build допустим только после успешной сборки именно нужной конфигурации.
Иначе можно случайно запустить старую DLL и принять результат за проверку новых исходников.
Lock-файл фиксирует версии зависимостей; он не заменяет доступность самих пакетов.

## Устройство одного теста

Удобна последовательность «подготовка → действие → проверка».
Подготовка создаёт минимальные данные, действие вызывает одну интересующую операцию,
проверка сравнивает наблюдение с ожидаемым результатом. Встроенные Check-проверки уроков используют эту же идею,
но являются консольным учебным стендом. MSTest умеет обнаруживать методы по атрибутам,
группировать результаты и показывать их в Test Explorer.

```csharp
[TestClass]
public sealed class CatalogBehavior
{
    [TestMethod]
    public void RemovingBookDoesNotReuseItsId()
    {
        var catalog = new LibraryCatalog();
        catalog.Add("Первая", "Автор", 2000);
        catalog.Remove(1);

        var added = catalog.Add("Вторая", "Автор", 2001);

        Assert.AreEqual(2, added.Id);
    }
}
```

Фрагмент показывает устройство теста; полноценные тесты с using и проектной ссылкой находятся в capstone.
Здесь важен публичный результат Add, а не частное устройство списка.
Если заменить List на Dictionary и сохранить контракт, тест должен продолжить работать.
Тесты, привязанные к имени частного поля или порядку внутренних вспомогательных вызовов без нужды,
мешают полезному рефакторингу.

Название теста сообщает ситуацию и ожидание. «Test1» мало помогает при падении сборки.
Слишком большой тест с десятком несвязанных действий трудно диагностировать.
Интеграционный сценарий может быть длинным, но его шаги должны образовывать один пользовательский путь.

## Границы, классы эквивалентности и мутанты

Для допустимого года 1450..2100 важны нижняя граница, верхняя граница и соседи за ними.
Обычный 2000 год не обнаружит ошибку в сравнении на краю.
Для проходного балла от 60 значения 59 и 60 различают строгую и нестрогую границу.
Выбирайте вход по причине возможной ошибки, а не только по удобству вычисления.

Класс эквивалентности объединяет входы, которые должны обрабатываться одним правилом.
Для парсера можно выделить корректные цифры, корректный синтаксис за диапазоном,
пустоту, неверные символы и EOF. Эти группы отличаются причиной отказа.
Пример «82» вместо «81» обычно не добавляет нового класса.
При этом регулярное повторение темы в новом контексте допустимо, если меняется проверяемое свойство:
позднее нас может интересовать сохранность файла при отказе, а не сам синтаксис числа.

Мутант — намеренно неправильная версия, например > вместо >= или удаление дубликатов при сортировке.
Если все проверки проходят и на мутанте, набор недостаточно различает поведение.
В задачах 16-01, 16-08 и 16-12 этот принцип проверяется исполняемо.
Мутационный эксперимент не обязан проверять все мыслимые ошибки; он делает слабость конкретного набора видимой.

Свойства иногда сильнее отдельных ожидаемых массивов.
У сортировки есть как минимум два независимых требования: порядок и сохранение мультимножества.
Совпадение суммы не доказывает сохранение элементов: [1,4] и [2,3] имеют одинаковую сумму.
Повторное применение сортировки должно сохранять результат, но и это свойство само по себе
не обнаружит функцию, всегда возвращающую пустой массив. Свойства нужно сочетать.

## Изоляция и воспроизводимость

Тест не должен зависеть от того, какой другой тест был выполнен раньше.
Общие статические списки, часы, случайные числа и настоящие пользовательские файлы являются скрытым вводом.
Для даты лучше передать today параметром. Для вывода — TextWriter.
Для хранения — интерфейс и отдельный тестовый двойник. Случайный вход при необходимости получает фиксированный seed,
а обнаруженный контрпример сохраняется как конкретный регрессионный случай.

Тестовый двойник не всегда должен повторять всю инфраструктуру.
Для проверки сообщения после сохранения достаточно callback, который считает вызовы или бросает IOException.
Если задача проверяет настоящий формат JSON, двойник уже недостаточен: нужен реальный сериализатор
и временный файл. Выбор границы проверки определяется свойством, которое требуется доказать.

Временная папка создаётся с уникальным именем и удаляется в finally.
Тест хранит точный созданный путь; удалять найденные по общему шаблону папки нельзя.
Испорченные документы создаются только внутри этой папки.
Для отрицательного сценария полезно сравнить байты файла до и после:
один код ошибки не гарантирует, что данные остались прежними.

Разные платформы используют разные переводы строк. Разрешайте только оговорённую разницу,
например CRLF и LF, сохраняя пустые строки и пробелы. Trim способен скрыть ошибку форматирования.
Сравнение строк и порядок сортировки также должны явно выбирать Ordinal или нужную культуру.

## Асинхронные проверки

Асинхронный тест должен возвращать Task и ожидать проверяемую операцию через await.
Если просто вызвать метод и завершить тест, ошибка задачи может произойти после проверки.
Task.FromException возвращает задачу с ошибкой; само получение этого объекта не выбрасывает сохранённое исключение.
Оно наблюдается при await. Поэтому место try/catch и наличие await меняют результат.

Для координации полезны TaskCompletionSource с RunContinuationsAsynchronously и явно управляемая отмена.
Ожидать «ровно 100 миллисекунд» ради доказательства порядка ненадёжно:
нагрузка машины меняет время, не меняя логики. Проверяйте наступившие события, результаты и токены.
Отмена является отдельным исходом, а не пустым успешным результатом.

В консольном адаптере задания иногда используется GetAwaiter().GetResult(), чтобы подключить асинхронный
эксперимент к синхронному Run. В самом приложении цепочка сохраняется асинхронной до точки входа.
Этот приём не следует механически переносить в обработчик интерфейса: блокировка UI-потока имеет другие последствия.

## Отладка по воспроизведённой причине

Начните с самого маленького входа, который нарушает контракт.
Запишите ожидаемое значение до запуска. Поставьте точку останова перед первым подозрительным изменением,
посмотрите локальные переменные и стек вызовов. Перед каждым F10 предскажите следующий шаг.
Если наблюдение расходится с прогнозом, уточните модель выражения или состояния.

При исключении различайте место исходного сбоя и окончательный обработчик.
Сообщение «ошибка файла» в CLI не говорит, был ли документ повреждён, отсутствовал доступ или отменена запись.
InnerException и стек помогают найти причину. Для пользователя нужны понятное сообщение и код,
для разработчика — воспроизводимый вход и проверка. Не выводите секретные данные ради диагностики.

После исправления запустите различающий тест, соседние сценарии и общую проверку.
Сохраните тест вместе с исправлением: иначе будущая переработка может вернуть дефект.
Не меняйте ожидаемое значение потому, что программа стабильно печатает другое.
Стабильная ошибка всё ещё остаётся ошибкой.

## От отдельных методов к приёмке

Модульный тест проверяет правило в памяти и быстро указывает место дефекта.
Файловый интеграционный тест связывает сериализатор, модель и файловую систему.
Сценарий отдельного процесса проверяет настоящие аргументы CLI и сохранение между запусками.
Успех одного уровня не заменяет остальные: метод Save может работать, а точка входа — выбирать другой путь.

В итоговом проекте сначала формулируется SPEC.md, затем выполняются этапы MILESTONES.md.
Готовый код служит разбором после самостоятельной реализации.
На защите нужно показать чистую сборку, тесты, перезапуск, повреждённый файл и небольшое изменение требования.
Отчёт проверки обязан отличать собранные заготовки от выполненных решений и реально проверенную ОС от предполагаемой переносимости.
