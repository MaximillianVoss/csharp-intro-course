# Строки, сравнение и границы Unicode

## 1. Сначала определить, что считается символом

Предварительно нужны методы, циклы и условия первых четырёх уроков. Цель занятия — уверенно обрабатывать текст, не смешивая индекс строки, скаляр Unicode и воспринимаемый текстовый элемент. Базовые задачи работают с явно ограниченным алфавитом; повышенные показывают случаи, где простое индексирование уже недостаточно. Начните с [выполняемого примера](examples/Program.cs), затем решайте [задачи](TASKS.md); [подробные ответы](SOLUTIONS.md) объясняют причины отказов и выбранные границы API.

В условии строковой задачи нужно уточнять не только максимальную длину, но и её единицу. «Первые десять символов» может означать десять кодовых единиц UTF-16, десять скалярных значений либо десять текстовых элементов. Для имени пользователя это разные контракты. В этом уроке слова используются явно: `Length` относится к UTF-16, Rune — к скалярам, StringInfo — к текстовым элементам. Ни одно из этих чисел не обещает ширину в колонках терминала.

Также различайте null и пустой текст. Null означает отсутствие строкового значения, `""` — существующий текст нулевой длины. Какие методы принимают null и какой результат возвращают, сказано в каждом условии. Если задача гарантирует корректный UTF-16, не нужно выдумывать политику для одиночных суррогатов. Но нельзя самовольно обещать ту же безопасность методу, который такие входы не проверяет.

## 2. Индексы, подстроки и неизменяемость

Индексы начинаются с нуля. У строки длины n допустимы индексы от 0 до n-1. Проверка `index <= text.Length` ошибочна: равенство уже выходит за последний char. Для потенциально отсутствующего text сначала проверяют null и только потом читают Length. Выражение `text[index]` возвращает char; границы его смысла уточним ниже.

Substring получает начальную позицию и, в одной из перегрузок, длину фрагмента. Это не конечный индекс. Если двоеточие найдено в позиции p, текст после него начинается с p+1. Значение -1 от IndexOf означает отсутствие совпадения и не может передаваться как обычный индекс. При p=Length-1 хвост пуст: `Substring(Length)` допустим. Такие крайние случаи лучше выписать до запуска.

Строковое значение неизменяемо. Рассмотрим самостоятельный пример:

```csharp
string original = "banana";
string copy = original;
copy = copy.Replace('a', 'o');
Console.WriteLine(original);
Console.WriteLine(copy);
```

Будут выведены banana и bonono. Присваивание сначала обозначает то же строковое значение двумя переменными. Replace возвращает результат замены, а присваивание сохраняет его только в copy. Если результат вызова не сохранить, исходный текст останется и там. Неизменяемость строки не запрещает менять значение переменной string: это разные уровни рассуждения.

Для коротких понятных выражений объединение строк через `+` нормально. В большом цикле последовательные добавления могут многократно создавать растущие промежуточные строки. Перед выбором другого инструмента сначала убедитесь, что он действительно решает задачу накопления, а не заменяет прозрачное одноразовое выражение сложной конструкцией.

## 3. Техническое сравнение и пользовательская культура

Сравнение должно соответствовать смыслу данных. Для команды, ключа протокола или служебного фрагмента обычно требуется явный Ordinal либо OrdinalIgnoreCase. Первое учитывает регистр, второе задаёт нечувствительное к регистру техническое сопоставление. Это другой вопрос, чем удобная для читателя сортировка слов определённого языка. В [рекомендациях Microsoft](https://learn.microsoft.com/en-us/dotnet/standard/base-types/best-practices-strings) такие сценарии рассматриваются раздельно.

Не заменяйте сравнение по умолчанию парой ToLower без осознанного выбора культуры. Кроме дополнительных строк, такой код скрывает правило сопоставления. Явный `string.Equals(text, expected, StringComparison.OrdinalIgnoreCase)` одновременно сообщает политику и безопасно принимает null. Пробелы при этом остаются значимыми; Trim — отдельное преобразование, которое нельзя добавлять без разрешения условия.

Культура нужна и при разборе чисел. Для ru-RU десятичным разделителем служит запятая, для en-US — точка. Передайте CultureInfo непосредственно в TryParse, а не меняйте настройку всего процесса. NumberStyles определяет дополнительные разрешения. Если группировка тысяч запрещена, флаг AllowThousands не должен появляться в выбранном наборе. Иначе чужой десятичный разделитель может быть принят с другим смыслом.

Тестировать культурную политику лучше парой одинаковых строк при разных явно заданных культурах. `"1,5"` должен успешно читаться в русском договоре и отвергаться в английском договоре без группировки. Это повторяемый тест, не требующий угадывать культуру компьютера. В техническом файле или сетевом протоколе часто выбирают InvariantCulture, чтобы формат не зависел от пользователя; файловые задачи появятся позже.

## 4. Один проход и построение результата

StringBuilder предоставляет изменяемый буфер для накопления текста: создаём `new StringBuilder()`, добавляем фрагменты через Append и получаем окончательную строку через ToString. Пока достаточно знать этот интерфейс готового библиотечного компонента; самостоятельно проектировать его класс не требуется. Назначение и основные операции описаны в [документации StringBuilder](https://learn.microsoft.com/en-us/dotnet/standard/base-types/stringbuilder).

Например, при схлопывании пробельных промежутков нельзя просто заменить `"  "` на `" "` один раз: длинная серия останется частично двойной, а табуляция вообще не затронется. Лучше один раз пройти по входу и держать флаг отложенного пробела. Он устанавливается после уже записанного текста, но сам пробел добавляется только перед следующим непробельным char. Так начальные и конечные разделители естественно исчезают.

Foreach последовательно выдаёт элементы источника. В `foreach (char ch in text)` это кодовые единицы строки. По сравнению с for не требуется вручную управлять индексом, но сама единица обхода не становится автоматически целой графемой. Если нужен индекс первого совпадения, for бывает яснее. Если нужен только char для копирования или проверки алфавита, foreach убирает лишний счётчик.

При разборе кавычек полезно формулировать маленькую грамматику. Внешняя пара ограничивает поле, а внутренняя кавычка допустима только как часть удвоенной пары. После такой пары продвигаются на два char. Частично построенный результат хранится локально и передаётся через out только после полного успеха. Это не готовый парсер всего CSV: точный объём обещания записан в условии.

## 5. UTF-16 и Rune

В .NET string хранит последовательность кодовых единиц UTF-16. Char представляет одну такую единицу. Многие привычные буквы помещаются в один char, но некоторые значения Unicode кодируются суррогатной парой. Поэтому у строки `"😀"` Length равна 2, хотя один скаляр задаёт весь эмодзи. Индексация [0] возвращает старший суррогат, [1] — младший; по отдельности это не целые скаляры.

Rune представляет скаляр Unicode, исключая суррогатный диапазон как самостоятельные значения. `text.EnumerateRunes()` позволяет последовательно получать такие элементы без ручного склеивания пары. Для первого скаляра можно взять первый Rune и вернуть его ToString. Это даёт одну или две кодовые единицы в результате. Основной контракт типа подтверждает [справка Rune](https://learn.microsoft.com/en-us/dotnet/api/system.text.rune?view=net-10.0).

При этом скаляр не равен воспринимаемому знаку. Буква e и следующий комбинируемый акцент — два скаляра, которые обычно отображаются совместно. Поэтому FirstScalar для `"e\u0301"` возвращает e без акцента. Это правильный результат именно скалярного контракта. Если требуется один целый текстовый элемент, нужен другой уровень обработки.

Для ASCII-ключа, напротив, вся эта сложность может быть сознательно исключена грамматикой. Проверка `'0' <= ch && ch <= '9'` означает именно десять ASCII-цифр. Char.IsDigit имеет более широкий смысл и может принять цифры других письменностей. Не следует объявлять одну проверку универсально правильной: они реализуют разные требования. Валидация протокола должна сохранять явно выбранный алфавит.

## 6. Текстовые элементы и нормализация

StringInfo даёт операции в терминах текстовых элементов. Созданный для строки объект имеет LengthInTextElements и SubstringByTextElements. В задачах префикс по элементам ограничивается минимумом запрошенного количества и фактической длины. Так нельзя разрезать акцентированную последовательность или проверяемый семейный ZWJ-эмодзи посередине. API и определение элементов описаны в [справке StringInfo](https://learn.microsoft.com/en-us/dotnet/api/system.globalization.stringinfo?view=net-10.0).

| Проверяемый текст | UTF-16 char | Скаляры | Текстовые элементы в .NET 10 |
| --- | --- | --- | --- |
| `a` | 1 | 1 | 1 |
| `😀` | 2 | 1 | 1 |
| `e` + `\u0301` | 2 | 2 | 1 |
| `👨‍👩‍👧‍👦` | 11 | 7 | 1 |

Таблица является набором конкретных проверенных примеров, а не формулой для любого текста. Unicode-правила и данные версионируются; курс привязан к заявленной среде .NET 10. Выбор шрифта, движок отображения и ширина терминала всё ещё могут влиять на внешний вид. Подсчёт текстовых элементов не обещает измерение пикселей или колонок.

Нормализация отвечает на ещё один вопрос: считать ли канонически эквивалентные записи равными. Предсоставленная é и последовательность e+акцент могут быть приведены к FormC и затем точно сравнены. Это не удаление акцентов, не смена регистра и не объединение похожих букв разных алфавитов. FormKC включает совместимые преобразования и реализует более широкий контракт. Поведение и ограничения описаны в [справке Normalize](https://learn.microsoft.com/en-us/dotnet/api/system.string.normalize?view=net-10.0).

В упражнениях нормализации вход гарантированно корректный UTF-16. Если приложение допускает произвольные одиночные суррогаты, нужно отдельно решить политику отказа или замены. Не расширяйте учебный контракт молча. Полный обзор терминов доступен во [введении в кодировки .NET](https://learn.microsoft.com/en-us/dotnet/standard/base-types/character-encoding-introduction).

## 7. Проверки, которые различают ошибочные модели

Строка из трёх ASCII-букв не обнаружит ошибку «Length равно числу видимых знаков»: на ней несколько моделей случайно совпадают. Нужен эмодзи вне BMP, затем комбинируемая последовательность и составной ZWJ-пример. Каждый отвечает на отдельный вопрос: целостность пары, отличие скаляра от элемента и группировка нескольких скаляров.

При проверке первого скаляра ошибочная реализация Substring(0,1) должна реально запускаться. Тест не ограничивается словами «это неверно»: он наблюдает длину 1, старший суррогат и отличие от целого эмодзи. Для текстового элемента проверяется сохранение всей последовательности с акцентом. Для нормализации проверяются не только равные формы é, но и неравенство ① и 1, чтобы не принять слишком широкую совместимость.

В обычных строковых алгоритмах по-прежнему важны пустота, начало, конец и отсутствие совпадения. Для неперекрывающегося поиска aaaaa/aa даёт два результата; сдвиг на один вместо длины образца даст иной ответ. Пустой образец нужно обработать до цикла, чтобы продвижение не остановилось. Для присваивания по первому = проверяйте дополнительный = внутри значения: разбиение по всем разделителям потеряло бы часть входа.

Отладка строится от контракта к конкретной единице текста. Сначала посмотрите Length и числовые значения char, затем число Rune, затем границы StringInfo. Не меняйте индекс наугад, пока не определили, какую величину он измеряет. Это помогает локализовать ошибку на правильном уровне и сохраняет ясность алгоритма.

## 8. Самопроверка и подробные ответы

Ответьте до чтения объяснений: меняет ли Replace исходную строку? Можно ли индексировать text[Length]? Почему OrdinalIgnoreCase подходит команде, но не описывает сортировку слов? Чему равны три длины у e с акцентом? Какой тест отличает первый Rune от первого char? Почему FormC не превращает все похожие знаки в один?

Ответ 1. Replace возвращает результат, который нужно сохранить; другие переменные с прежним строковым значением не меняются. Ответ 2. Нет: последний допустимый индекс Length-1, а пустая строка вообще не имеет элементов. Ответ 3. Техническое сопоставление не опирается на лингвистические правила порядка конкретного языка. Культуру и режим сравнения нужно выбирать по назначению данных.

Ответ 4. У `e\u0301` две кодовые единицы, два скаляра и один текстовый элемент в проверяемой среде. Ответ 5. Эмодзи вне BMP занимает два char и один Rune; Substring(0,1) вернёт половину пары. Однако этот тест ещё не доказывает сохранение целой графемы: для этого нужен акцент или ZWJ-последовательность. Ответ 6. Каноническая нормализация объединяет определённые эквивалентные записи, а не визуальное сходство. Поэтому регистр, пробелы и совместимые отличия могут оставаться значимыми. Точный ответ должен сначала назвать договорённость задачи, а затем выбранный инструмент обработки.
