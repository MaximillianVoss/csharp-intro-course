# Урок 13. Делегаты, лямбды и события

Перед уроком нужны методы, классы, интерфейсы, коллекции, обобщения и исключения. Теперь переменной можно будет передать не только данные, но и способ их обработки. Вы научитесь читать сигнатуры `Func`, `Action`, `Predicate`, объяснять замыкание и проверять число вызовов. В конце небольшой реестр команд покажет, как отделить постоянный алгоритм от меняющихся действий без большого условного оператора.

## 1. Поведение как значение

Допустим, один метод должен применять к числу разные операции. Можно добавить параметр с кодом режима и растущий switch, а можно передать саму операцию. Делегат — типобезопасное значение, представляющее вызываемый метод или список методов с совместимой сигнатурой. Он знает, какие аргументы принимает и какой результат возвращает.

```csharp
Func<int, int> transform = x => x + 3;
int result = transform(4);
```

Здесь `Func<int,int>` принимает int и возвращает int. В группе параметров `Func` последний тип относится к результату, предшествующие — к аргументам. `Action<string>` принимает string и ничего не возвращает. `Predicate<int>` принимает int и возвращает bool. Выбирайте форму, которая раскрывает роль: предикат естественно читается как правило допуска, Action — как уведомление.

Присваивание делегата не выполняет его тело. Вызов появляется при записи `transform(4)` либо `transform.Invoke(4)`. Поэтому фабрика составного правила может проверить конфигурацию сейчас, а запускать правила позже. Из этой разницы следуют важные тесты: создание конвейера не должно случайно читать файл, менять счётчик или отправлять уведомление.

Делегат не обязан быть анонимной функцией. Можно передать имя совместимого существующего метода, например `list.Add` как `Action<T>`. Выражение метода и его вызов различаются скобками: `list.Add` передаёт поведение, `list.Add(value)` выполняет его немедленно.

## 2. Лямбда и договор о вызовах

Лямбда `x => x * x` задаёт короткую функцию. Слева параметры, справа выражение или блок с `return`. Типы параметров обычно выводятся из ожидаемого типа делегата. Сложное тело удобнее писать блоком, а повторно используемую большую операцию — отдельным именованным методом. Краткость не оправдывает неясный порядок действий.

Контракт метода с делегатом включает больше, чем тип результата. Он может обещать ровно один вызов на элемент, определённый порядок, остановку при исключении и проверку null до обработки. Предикат способен считать вызовы или менять состояние. Поэтому два вызова вместо одного являются наблюдаемой ошибкой, даже если на чистой функции итог совпал.

```csharp
static int Apply(int value, Func<int, int> operation)
{
    ArgumentNullException.ThrowIfNull(operation);
    return operation(value);
}
```

Проверка null здесь выполняется при Apply. Если метод возвращает новую лямбду, размещение проверки внутри неё отложило бы обнаружение ошибки до будущего вызова. Обычно неверные зависимости лучше отклонять при создании. При этом исключение самой операции не следует автоматически превращать в ноль: вызывающий имеет право увидеть реальную причину неуспеха.

В тестах сохраняйте результат операции в одну переменную, затем отдельно проверяйте счётчик и порядок. Не вызывайте тестируемый метод ещё раз только ради красивой строки вывода: при функциях с состоянием это уже другая последовательность событий.

## 3. Захват переменной

Лямбда может обратиться к локальной переменной внешнего метода. Компилятор сохраняет необходимое состояние так, чтобы оно жило и после возврата внешнего метода. Такое сочетание функции и захваченного окружения называется замыканием.

```csharp
int factor = 2;
Func<int, int> multiply = value => value * factor;
int first = multiply(3);
factor = 5;
int second = multiply(3);
```

Получатся 6 и 15. Захвачена переменная `factor`, а не автоматически сделанная копия числа 2. Её значение читается при каждом выполнении тела. Если требуется снимок, создайте отдельную переменную и не меняйте её: `int saved = factor;`. Это решение должно отражать нужный смысл, а не быть механическим приёмом для всех лямбд.

Частая ошибка появляется в `for`: все функции `() => i` обращаются к одной переменной индекса. После окончания цикла она содержит предельное значение, поэтому функции возвращают одно и то же. Локальная `int copy = i;` внутри тела создаёт отдельное место хранения на итерацию. Проверять нужно после окончания цикла, иначе ошибка останется незаметной.

Замыкание может удерживать ссылки на крупные объекты. Пока делегат доступен, необходимые захваченные данные тоже могут оставаться доступными. Для базового курса достаточно осознанно выбирать, какие переменные захватываются и кто хранит делегат. Не добавляйте глобальное состояние, чтобы «исправить» время жизни: это часто создаёт ещё более широкую и непредсказуемую связь.

## 4. Композиция и короткое замыкание

Композиция строит новую функцию из существующих. Если нужен порядок first, затем second, результат имеет вид `x => second(first(x))`. Для `x+1` и `x*2` при входе 3 получится 8; обратный порядок дал бы 7. Значения специально выбраны так, чтобы тест различал эти две правдоподобные реализации.

Правила допуска можно объединять логическим И. Выполняйте их по порядку до первого false. Это короткое замыкание полезно не только для скорости: второе правило может рассчитывать, что первое уже проверило допустимость объекта. Если сначала вычислить результаты всех предикатов в массив, такая гарантия исчезнет.

Пустой набор условий для И принимает любое значение: нет нарушенного требования. Это правило нужно явно указать в задаче. Для ИЛИ аналогичная пустота дала бы false. Исключение правила отличается от его ответа false: оно сообщает сбой выполнения и обычно распространяется, если задача не задаёт отдельную политику обработки.

Если фабрика получает массив правил, подумайте о владельце массива. Его копия фиксирует состав конвейера: вызывающий не заменит правило изменением исходной ячейки. При этом копируются ссылки на делегаты, а не их внутренние замыкания. Состояние самих правил может оставаться общим. Такой предел защиты важно понимать, чтобы не обещать полной неизменяемости.

## 5. Стратегия, callback и декоратор

Один и тот же механизм делегата играет разные роли. Стратегия выбирает способ вычисления: normalizer преобразует строку, а общий алгоритм знает лишь последовательность шагов. Callback уведомляет о завершении шага: Action получает новую накопленную сумму. Декоратор оборачивает другую функцию дополнительным поведением: кэшом, проверкой или журналированием.

В конвейере «нормализовать, записать в журнал, вернуть» результат normalizer сохраняют один раз. Повторный вызов ради журнала может вернуть другое значение и нарушить число обращений. Все обязательные зависимости проверяют до первого действия. Если logger равен null, не стоит сначала выполнять преобразование с побочными эффектами и только затем обнаруживать неверную конфигурацию.

Пример декоратора — мемоизация. Замыкание хранит `Dictionary<int,int>`. При попадании возвращает сохранённый результат; при отсутствии вызывает исходную функцию и добавляет успешное значение. Ноль должен кэшироваться как обычный результат. Исключение не добавляется, если договор требует повторить попытку в следующий раз. Запись в словарь располагают после успешного вычисления.

Такой кэш не становится автоматически многопоточным, ограниченным по памяти или подходящим для любой функции. Если исходная функция зависит от меняющегося внешнего состояния, прежний результат может устареть. В учебной задаче границы заданы явно: один поток, независимые кэши декораторов и только успешные вычисления. Сначала докажите эту модель, затем обсуждайте расширение.

## 6. Многоадресный делегат и событие

Через `+=` делегат может получить несколько обработчиков. Они вызываются по порядку регистрации. Если один бросил исключение, обычный многоадресный вызов прекращается, а последующие не выполняются. Если контракт требует собрать ошибки и продолжить, нужен явный обход отдельных обработчиков с отдельным try/catch вокруг каждого. Один catch вокруг всего цикла не решает задачу.

`event` ограничивает внешнюю работу с делегатом. Внешний код подписывается и отписывается, но не присваивает список целиком и не вызывает событие произвольно. Владелец класса решает, когда состояние изменилось и пора уведомлять. Например, счётчик сообщает о переходе из области ниже порога в область не ниже порога.

Важно обновить состояние до вызова события, если подписчик должен видеть новое значение. Исключение подписчика тогда не отменяет уже совершённый переход. Это не транзакция, если откат отдельно не реализован. Проверка только `Value >= threshold` отправляла бы событие на каждом шаге выше границы, а сравнение old и next обнаруживает именно переход.

Для отписки сохраните делегат: `Action<int> listener = ...;`. Потом `-= listener` снимет тот же обработчик. Новая похожая лямбда обычно является другим делегатом и не обязана удалить прежнюю. Также помните: подписка может продлить доступность подписчика, пока издатель события хранит его обработчик.

## 7. Проверка взаимодействий и отладка

Для обычной функции часто достаточно проверить результат. Для делегатов дополнительно проверяйте протокол: сколько раз вызвали зависимость, с какими аргументами, в каком порядке и что произошло после ошибки. Список строк `trace` делает порядок видимым без внешнего журнала и случайных измерений времени.

Тесты должны обнаруживать конкретные неправильные варианты. На смешанном наборе `[1,2,4]` чистая чётность даст count=2 и при одном вызове, и при ошибочном `accept(x) && accept(x)`. Но счётчик покажет 3 против 5 обращений. Для композиции нужны некоммутирующие операции. Для захвата в цикле делегаты вызываются после его завершения. Для короткого замыкания последующее правило имеет наблюдаемый эффект.

При сбое сначала найдите точное место вызова. Создание лямбды, регистрация события и исполнение тела могут происходить в разных частях программы. Поставьте точку останова внутри callback и посмотрите стек вызовов. Проверьте захваченные переменные в момент исполнения, а не только при создании делегата.

Не включайте взаимодействие с реальными пользователями, сетью и файлами ради теста реестра команд. Передайте обработчики, записывающие наблюдения в список. Тогда проверка детерминированно показывает маршрутизацию, аргументы и число вызовов. Конкретное действие команды можно разрабатывать отдельно от механизма её поиска.

## 8. Самопроверка с ответами

Перед ответами сформулируйте самостоятельно: что возвращает последний тип Func; когда читается захваченная переменная; почему новая лямбда не всегда отписывает старую; кто вызывается после ошибки multicast; какие данные сохраняет мемоизация.

Ответ 1. Последний параметр типа `Func` — тип результата, предыдущие задают аргументы. В `Func<string,int,bool>` два аргумента и результат bool. Если результата нет, удобен Action, а не Func с искусственным возвращаемым значением.

Ответ 2. Переменная читается при исполнении тела лямбды. Изменение общего factor после создания делегата меняет будущие результаты. Для фиксированного значения нужен отдельный снимок; его смысл и время создания выбираются явно.

Ответ 3. Отписка сравнивает делегаты, а не только похожесть текста исходника. Сохранение обработчика в переменную гарантирует, что вы передаёте именно зарегистрированное значение. В противном случае подписка может продолжить работать.

Ответ 4. Обычный многоадресный вызов прекращается на первом исключении. Продолжение требует другого, явно написанного протокола изоляции ошибок. Такой протокол стоит тестировать отдельно, потому что он меняет наблюдаемое поведение.

Ответ 5. В описанной задаче кэш хранит только успешные результаты по аргументу, включая ноль. Ошибки не кэшируются. Разные вызовы фабрики имеют отдельные словари, но один возвращённый делегат сохраняет свой словарь между обращениями.
