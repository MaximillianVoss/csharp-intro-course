# Модуль 09. Интерфейсы, наследование и подстановка

## 1. Контракт важнее конкретного класса

Нужны собственные классы, свойства, конструкторы, композиция и стандартные коллекции. Задача модуля — сделать части программы заменяемыми и проверить, что замена сохраняет обещанное поведение. Запустите [пример](examples/Program.cs), затем работайте с [условиями](TASKS.md). В [разборах](SOLUTIONS.md) обращайте внимание на вызовы через общий тип, а не только на объявления классов.

Представим расчёт общей площади. Если метод знает все классы фигур поимённо и выбирает формулу через проверки типа, новая фигура требует изменения этого метода. Вместо перечисления конкретных типов можно договориться об операции `Area`. Тогда каждая фигура вычисляет её самостоятельно, а суммирующая сторона знает только общий контракт.

Контракт состоит не только из сигнатуры. Свойство площади должно возвращать площадь, а не периметр; очередь должна отдавать элементы в порядке FIFO; репозиторий-снимок должен защищать сохранённые данные от изменения снаружи. Компилятор проверит соответствие имён и типов, но смысл этих обещаний подтверждают анализ и тесты.

Интерфейс C# задаёт общий набор членов для разных типов. Здесь используются простые объявления без реализации: свойства и методы, которые классы обязаны предоставить. Более сложные возможности современных интерфейсов не нужны для освоения подстановки. Базовую модель можно сверить с [официальным руководством Microsoft](https://learn.microsoft.com/en-us/dotnet/csharp/fundamentals/types/interfaces).

## 2. Реализация интерфейса и динамический выбор поведения

```csharp
public interface IShape
{
    double Area { get; }
}

public sealed class Triangle : IShape
{
    private readonly double width;
    private readonly double height;
    public Triangle(double width, double height)
    {
        this.width = width;
        this.height = height;
    }
    public double Area => width * height / 2;
}
```

После двоеточия класс указывает реализуемый интерфейс. Публичное свойство с подходящим именем и типом выполняет контракт. Создать сам интерфейс через `new IShape()` нельзя, но можно хранить ссылку на подходящий объект: `IShape shape = new Triangle(3,4)`. Статический тип переменной ограничивает доступные операции контрактом.

При чтении `shape.Area` выбирается реализация фактического объекта. Это полиморфизм: одна операция имеет разные реализации. В массиве `IShape[]` могут лежать прямоугольники и треугольники, а один цикл суммирует их площади. Внешний код не обязан приводить ссылку обратно к конкретному классу.

Интерфейсная ссылка не создаёт копию объекта и не уничтожает его состояние. Если две ссылки ведут к одному изменяемому хранилищу, изменение через пишущий интерфейс видно через читающий. Ограничение доступных членов — средство проектирования API, а не автоматическое глубокое копирование. Обещание независимого снимка реализуют явно.

Один класс может реализовать несколько интерфейсов. Например, MemoryName поддерживает IReadName и IWriteName, а ReadOnlyName — только IReadName. Метод построения заголовка принимает читающий контракт и поэтому подходит обоим. Требование лишних возможностей заставило бы read-only реализацию придумывать бессмысленный или запрещённый Write.

Ключевой вопрос проектирования: какие операции действительно нужны этому потребителю? Маленький интерфейс облегчает использование и замену зависимости. Но не следует дробить каждый метод механически: контракт должен отражать связную роль, которую вызывающий способен осмысленно использовать и проверить.

## 3. Наследование, abstract, virtual, override и new

Класс может наследовать один базовый класс и реализовать несколько интерфейсов. Базовый класс полезен, когда есть общая реализация или согласованная рамка алгоритма. Абстрактный класс не создаётся напрямую и может оставлять отдельные части наследникам. Модификатор `protected` делает член доступным внутри класса и его наследников, скрывая его от обычного внешнего вызова.

Для тарифов доставки база задаёт публичный расчёт: сложить базовую плату и переменную часть, затем применить минимум. Конкретный Ground определяет числа и формулу переменной части, но не меняет последовательность расчёта. Такой шаблонный метод предотвращает ситуацию, когда один тариф забывает минимальную стоимость.

Виртуальный метод обозначается `virtual`; наследник меняет его через `override` с совпадающей сигнатурой. Тогда вызов через базовую ссылку выбирает переопределённую реализацию. `abstract` означает, что обязательной реализации в данном классе нет; подходящий конкретный наследник должен её предоставить.

```csharp
public class Printer
{
    public string Describe() => "base description";
    public virtual string Render() => "base render";
}
public sealed class FancyPrinter : Printer
{
    public new string Describe() => "fancy description";
    public override string Render() => "fancy render";
}
```

Если `Printer parent = new FancyPrinter()`, вызов `parent.Describe()` вернёт базовое описание, а `parent.Render()` — fancy render. `new` скрывает невиртуальный член и выбирается по статическому типу ссылки; `override` участвует в виртуальном выборе по объекту. Оба вызова относятся к одному объекту, поэтому объяснение через «создались два принтера» неверно.

Перегрузка — ещё одна отдельная идея. `Speak(string suffix)` не заменяет базовый `Speak()`, потому что принимает другой набор параметров. Если намеревались переопределить метод, `override` помогает компилятору обнаружить несовпадение. Проверяйте исправление именно через базовую ссылку: прямой вызов нового метода может скрыть исходную проблему.

Не используйте наследование просто для доступа к чужим полям. Если отношения «является разновидностью» нет, композиция обычно выражает задачу яснее. Корзина содержит строки, декоратор содержит обработчик текста, сервис содержит часы. Эти отношения не требуют объявлять корзину строкой, а сервис — часами.

## 4. Внедрение зависимостей вручную

Зависимость — объект или возможность, без которой данная часть программы не выполнит работу. Налоговая политика нужна счёту, часы — приветствию, канал доставки — службе уведомлений. Если сервис создаёт конкретную зависимость внутри метода, вызывающий не может заменить её, не редактируя сервис.

```csharp
public sealed class Invoice
{
    private readonly ITaxPolicy policy;
    public Invoice(ITaxPolicy policy)
    {
        this.policy = policy;
    }
    public decimal Total(decimal net) => net + policy.Tax(net);
}
```

Теперь сборка происходит снаружи: `new Invoice(new RateTax(0.2m))` или `new Invoice(new NoTax())`. Это ручное внедрение через конструктор. Контейнер, веб-фреймворк, глобальные настройки и сторонние пакеты для него не нужны. Конструктор делает зависимость явной, а readonly-поле сохраняет выбранную стратегию на время жизни объекта.

Здесь зависимости по условиям не `null`. В прикладном API отсутствие обязательной зависимости обычно проверяется на границе создания; исключения будут следующей темой. Важно не подменять внедрение скрытым резервным `new RateTax(...)` внутри Total: тогда часть вызовов снова начнёт зависеть от жёстко заданного решения.

Часы показывают пользу для тестирования. Если приветствие читает `DateTime.Now`, его результат меняется со временем. Интерфейс IClock позволяет передать FixedClock с известным часом. Тогда граница между утром и днём в 12:00 проверяется независимо от момента запуска. Не нужно ждать полудня, менять системное время или сравнивать длительность выполнения.

Тестовая зависимость может также записывать обращения. Счётчик вызовов обнаруживает лишнее чтение источника, журнал канала — порядок и сообщения. Подмена не обязательно имитирует всю настоящую систему: достаточно реализовать контракт, необходимый этому тесту. Чем уже контракт, тем проще подготовить достоверную замену.

## 5. Составные объекты: дерево, обёртка, резерв

Композиция позволяет строить новые реализации из существующих. У дерева размеров и файл, и папка реализуют INode.Size. Лист возвращает собственный размер, папка суммирует Size детей. Потребитель не различает лист и составной узел. Рекурсивное вычисление следует дереву; отсутствие циклов является важным предусловием учебного примера.

Декоратор оборачивает объект с тем же интерфейсом и дополняет его поведение. TrimDecorator сначала получает результат inner, затем обрезает края. PrefixDecorator сначала получает внутренний результат, затем добавляет префикс. Их можно соединять в разных порядках. Однако одинаковый набор шагов не гарантирует одинаковую строку, потому что операции обычно не коммутируют.

Для текста с пробелами `"  a  "` внутренняя обрезка даёт `"a"`, затем префикс `" > "` даёт `" > a"`. При обратном порядке сначала получается `" >   a  "`, внешняя обрезка даёт `">   a"`. Точные пробелы в тесте являются частью результата, а не косметикой вывода. Если декоратор обрабатывает вход вместо результата inner, контракт цепочки изменяется.

Резервный источник использует Try-контракт. Если primary вернул `true`, его значение окончательно, даже когда строка пустая. Только `false` разрешает обратиться к backup. Нельзя заранее вызвать оба и затем выбрать текст: лишний вызов может стоить ресурсов или иметь наблюдаемые последствия. Тест с журналом проверяет не только ответ, но и отсутствие ненужного обращения.

Эти три формы композиции решают разные задачи. Дерево агрегирует много детей, декоратор меняет результат одного объекта, резерв выбирает второй источник при отсутствии первого. Общая идея — поручать работу абстракциям — не отменяет различий в порядке вызовов и условиях остановки.

## 6. Подстановка проверяется поведением

Два класса с одинаковыми сигнатурами могут выполнять разные обещания. Queue-адаптер и Stack-адаптер оба способны предоставить Add и TryTake. Но только первый удовлетворяет FIFO. Если общий потребитель рассчитывает на порядок очереди, подстановка стека нарушает контракт, хотя программа успешно скомпилируется.

Общий проверяющий сценарий начинает с пустоты, добавляет 1 и 2, извлекает 1, добавляет 3, затем ожидает 2 и 3. Разные значения и перемежение операций отличают очередь от стека. Тест с одним элементом не различает эти реализации. Такой сценарий применяется через интерфейс, поэтому не привязан к именам внутренних полей.

У репозитория проверяйте обе границы владения. После Save измените исходный массив и убедитесь, что сохранённые данные прежние. После Load измените результат и снова загрузите данные. Один тест не заменяет другой: реализация может правильно копировать на входе и ошибочно отдавать внутренний массив на выходе, либо наоборот.

Явная реализация интерфейсов помогает при совпадающих именах членов. Один Report может отдельно реализовать `ICompactReport.Render()` и `IDetailedReport.Render()`. Вызов доступен через соответствующий интерфейс, а публичного неоднозначного Report.Render нет. В обычном дизайне часто подходят разные говорящие имена, но техника полезна для понимания нескольких контрактов одного объекта.

Цена абстракции должна быть соразмерна задаче. Интерфейс ради единственного простого вычисления не всегда помогает. Он полезен, когда есть реальные варианты поведения, внешняя изменчивая зависимость, независимый потребитель или необходимость общего контракта тестов. Избыточное количество пустых слоёв не делает маленькую программу автоматически качественной.

## 7. Отладка собранного приложения и вопросы

Для службы уведомлений начните с зависимостей в памяти: известный список адресатов, простой шаблон и записывающий канал. После SendAll проверьте число попыток, число успехов, порядок и текст каждой попытки. Отказ одного канала по контракту не останавливает остальные. Здесь не выполняется настоящая отправка: модель позволяет проверить координацию отдельно от внешнего сервиса.

Если результат неверен, выясните, какая реализация фактически передана конструктору. Затем проверьте статический тип ссылки и наличие virtual/override для наследования. Поставьте остановку внутри конкретного метода: это покажет маршрут вызова надёжнее догадки по имени переменной. Для цепочки обёрток запишите промежуточные строки в порядке возврата из внутренних вызовов.

Ответьте самостоятельно: что гарантирует компиляция интерфейса, а что остаётся проверить тестом? Чем перегрузка отличается от override? Когда нужен абстрактный класс? Почему пустая найденная строка не разрешает fallback? Почему часы внедряются через интерфейс? В каком порядке декораторы строят окончательный текст?

## 8. Ответы самопроверки

**Сигнатура и поведение.** Компилятор проверяет доступные члены, типы параметров и результата. Он не выводит FIFO, независимость копии или единичность обращения к каналу из имени интерфейса. Эти свойства задаются текстом контракта и подтверждаются наблюдаемыми сценариями. Неправильный Stack-адаптер намеренно демонстрирует эту границу.

**Перегрузка и переопределение.** Перегрузка добавляет метод с другим набором параметров. Override заменяет виртуальную реализацию того же контракта в наследнике. Если Animal вызывает Speak без аргументов, наличие Speak с суффиксом само по себе ничего не меняет. Проверка через базовую ссылку должна показать исправление.

**Абстрактная база.** Она уместна, когда можно разделить реализацию или защитить общий порядок алгоритма. В доставке база применяет минимум одинаково ко всем тарифам. Интерфейса достаточно, когда нужна только роль без общей реализации. Композиция подходит для содержания зависимостей, не являющихся разновидностями самого сервиса.

**Пустое найденное значение.** TryGet возвращает информацию о наличии отдельным bool. Строка `""` при true может быть намеренной настройкой. Повторный поиск заменил бы её чужим значением и нарушил приоритет primary. Поэтому fallback зависит от bool, а не от проверки длины строки.

**Часы.** Интерфейс отделяет решение от неконтролируемого времени. FixedClock даёт тесту входные данные для обеих сторон границы полудня. Тест остаётся повторяемым утром, ночью и на другом компьютере. Если внутри сервиса всё ещё читается DateTime.Now, внедрение не выполнено по существу.

**Порядок обёрток.** Вызовы идут внутрь цепочки до базового обработчика, а преобразования результата выполняются при возврате наружу. Поэтому внешняя обрезка видит уже добавленный внутренний префикс, а внешнее добавление префикса не попадает под внутреннюю обрезку. Проверять нужно точную строку вместе с пробелами.
