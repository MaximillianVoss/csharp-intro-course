# Методы, декомпозиция и отладка

## 1. Зачем выделять метод

Предварительно нужны выражения, ветвления и циклы первых трёх уроков. До этого объявления методов были предоставленными оболочками. Теперь вы сами определяете входы, результат и способ взаимодействия с вызывающим кодом. Итог занятия — несколько небольших методов с ясными контрактами и программа, в которой расчёт можно проверить отдельно от консоли. Пройдите [пример](examples/Program.cs), выполните [задачи](TASKS.md) разных форматов и после попытки изучите [разборы](SOLUTIONS.md).

Метод полезен не только для сокращения повторяющихся строк. Он даёт имя действию и границу ответственности. `ExpectedDigit(prefix)` сообщает, что здесь вычисляется ожидаемая контрольная цифра. Вызывающий код может не знать, как выделяются сотни и десятки, но должен понимать допустимый диапазон prefix и смысл результата. Слишком длинный метод часто смешивает несколько правил; слишком мелкие помощники без предметного смысла, напротив, заставляют прыгать между файлами без пользы.

Перед реализацией запишите контракт: какие аргументы допустимы, что возвращается на успехе, как обозначается отказ, какие внешние данные меняются. Не добавляйте чтение с клавиатуры в вычисление только потому, что итоговое приложение консольное. Метод, получающий значения аргументами, можно вызвать и из программы, и из автоматического теста. Это разделение пригодится позже в графическом интерфейсе и итоговом проекте.

## 2. Объявление, вызов и return

В файлах решений методы помещены внутрь предоставленного статического класса. Ключевое слово static в этом контексте позволяет вызывать метод без создания экземпляра; полноценную модель классов изучим в уроке 08. Пример вычисления:

```csharp
static int Add(int first, int second)
{
    int result = first + second;
    return result;
}

Console.WriteLine(Add(2, 3));
```

Здесь `int` перед именем определяет тип результата. Параметры first и second — локальные имена входных данных. Вызов подставляет аргументы 2 и 3. Return завершает текущий вызов и передаёт значение обратно. После него в этом пути метод уже не продолжает работу. Тип void означает отсутствие возвращаемого значения; это подходит для действия вроде записи в предоставленный TextWriter, но не заменяет bool при проверке успешности.

Метод с результатом обязан возвращать значение на каждом достижимом пути. Если `IsEven` возвращает true только внутри if и ничего не возвращает для нечётного числа, программа не компилируется. Компилятор не подставляет false автоматически. Когда требуемый результат уже является логическим выражением, можно вернуть его напрямую, не вводя дополнительное состояние.

Область видимости параметра ограничена методом. Имя result в одном методе не мешает такому же имени в другом. Не следует рассчитывать, что локальная переменная сохранит значение между вызовами. Каждый вызов получает своё состояние; обмен данными должен происходить через объявленный интерфейс, а не через случайное совпадение имён.

## 3. По значению, через ref и через out

Обычный int-параметр получает копию значения аргумента. Если внутри метода переставить a и b, внешние x и y останутся прежними. Это не ошибка компилятора: у метода было право менять только собственные копии. Для изменения внешней переменной в сигнатуре и в вызове явно указывают ref. Так место вызова само предупреждает читателя о возможном побочном эффекте.

Out предназначен для результата через параметр. Внешняя переменная не обязана иметь начальное значение, а метод обязан назначить out перед любым возвратом. Try-метод часто возвращает bool и передаёт полезное число через out. Но соглашение о значении out при false нужно определить отдельно: false не обнуляет его магически.

```csharp
static bool TryDouble(int value, out int doubled)
{
    doubled = 0;
    long candidate = (long)value * 2;
    if (candidate < int.MinValue || candidate > int.MaxValue) return false;
    doubled = (int)candidate;
    return true;
}

bool success = TryDouble(21, out int answer);
Console.WriteLine($"{success}:{answer}");
```

В отказном пути doubled остаётся нулём; при успехе получает 42. Проверка должна испытывать обе части контракта: bool и выходное число. Это особенно важно после успешного вызова, за которым следует отказный: старый результат не должен выглядеть новым.

Ref допускает алиасы: два параметра могут обозначать одну переменную. Для обмена это безопасно и оставляет значение прежним. Для часов и минут одна переменная не может одновременно хранить обе составляющие, поэтому задача явно требует разные переменные. Изменение нескольких ref лучше выполнять только после полной валидации и локального расчёта. При отказе обе исходные величины должны сохраниться; это проверяется отдельными утверждениями.

## 4. Имена аргументов, перегрузки и локальные помощники

Необязательный параметр имеет значение по умолчанию в объявлении. Например, quantity=1 означает именно одну единицу при пропуске, а не ноль и не неизвестность. Именованные аргументы связываются с именами параметров: `Total(10m, fee: 3m)` может пропустить quantity. Все именованные аргументы можно записать в ином порядке, если это улучшает читаемость. Сам метод получает готовые значения и не знает, в каком порядке они были написаны в исходнике.

Перегрузки имеют одно имя, но различимые наборы параметров. Выбор зависит от статических типов аргументов. Литерал 7 и переменная `var x=7` имеют int; литерал 7.0 и переменная `double y=7` имеют double. Поэтому даже одинаковое математическое значение может выбрать другую перегрузку. Возвращаемый тип сам по себе не позволяет объявить две иначе одинаковые перегрузки. Не создавайте набор почти одинаковых методов, если место вызова из-за него становится неоднозначным для человека.

Локальная функция объявляется внутри метода и нужна только там. Помощник Absolute для манхэттенского расстояния можно держать рядом с формулой, не добавляя его в общий интерфейс. Static у локального помощника запрещает ему зависеть от окружающих локальных переменных; всё нужное передаётся параметрами. Это облегчает чтение и проверку. Локальные функции не следует путать с лямбдами: делегаты и лямбды будут отдельной темой позже.

## 5. Декомпозиция без потери предметного правила

Рефакторинг сохраняет поведение, а не только красивый вид. В расчёте чека отдельно полезны базовая сумма, ставка скидки и оформление строки. Но разбиение не разрешает менять порядок округления. Если договорённость требует сначала округлить скидку, затем вычесть её из базовой суммы, итог должен согласовываться с напечатанными составляющими.

На цене 0.01 и количестве 15 базовая сумма равна 0.15. Ставка 10% даёт необработанную скидку 0.015. После округления AwayFromZero скидка становится 0.02, итог — 0.13. Если вычесть 0.015 и лишь затем округлить итог, получится 0.14. Оба пути выглядят разумно без точного условия, поэтому в задаче порядок указан прямо. Тест на этом входе является частью предметного контракта.

Чистый помощник не должен одновременно читать Console, менять культуру процесса и форматировать пользовательское сообщение. InvariantCulture можно передать непосредственно в нужное форматирование. Для вывода полезно принять TextWriter аргументом: тогда в приложении можно передать консоль, а в тесте строковый приёмник. Метод не должен закрывать переданный приёмник, если управление его сроком жизни не поручено явно.

При декомпозиции проверяйте помощники отдельно и затем их совместную работу. В контрольной цифре это помогает отличить неверное выделение сотен от ошибки в весах и от слишком поздней проверки диапазона. Не требуется тестировать каждую строку в изоляции; важно проверять отдельные договорённости, которые имеют самостоятельный смысл и разные причины отказа.

## 6. Рекурсия и стек вызовов

Рекурсивный метод вызывает себя для меньшей задачи. Нужны базовый случай и строгое приближение к нему. Для суммы цифр неотрицательного числа база — ноль, а уменьшение — целое деление на 10. Каждый вызов добавляет последнюю цифру к ответу для оставшегося префикса. Чтобы обработать int.MinValue, сначала переносим значение в long и затем получаем модуль.

Стек вызовов хранит отдельный кадр для каждого незавершённого вызова. У каждого кадра собственные параметры и ожидаемое продолжение. Для `Trace(2)` сначала идут вызовы 2→1→0, а готовые строки возвращаются в обратном порядке. Внешняя интерполяция не может закончиться до получения внутренней строки. Поэтому важно отличать действие перед рекурсивным вызовом от действия после него.

Рекурсия не является обязательной заменой циклу. Для десятка цифр глубина мала и хорошо объясняет механизм. Для неограниченного пользовательского n рекурсивное уменьшение на единицу может заполнить стек. Оценка глубины — отдельная часть допустимого диапазона. Также учитывайте построение строк: на каждом возврате могут создаваться новые фрагменты, поэтому число вызовов не всегда полностью описывает стоимость результата.

В двоичном возведении в степень рекурсия вовсе не нужна. Метод хранит результат, текущий множитель и оставшийся показатель. Нечётный бит домножает результат, показатель делится пополам, множитель возводится в квадрат только если понадобится дальше. Ненужный последний квадрат может переполниться при допустимом итоговом ответе: проверять нужно выполняемые промежуточные операции, а не одну финальную формулу.

## 7. Как отлаживать границу метода

До запуска сформулируйте ожидаемые аргументы и результат. Поставьте точку останова в месте вызова и проверьте, что аргументы действительно те, которые вы предполагали. Step Into позволяет войти внутрь метода, Step Over выполнить вызов целиком, а окно стека показывает цепочку вызовов. Названия команд и сочетания клавиш зависят от среды; в Visual Studio нужные действия доступны в меню отладки.

Если ошибка появляется в итоговом сообщении, сначала проверьте числовой результат до форматирования. Если числовой помощник верен, проверьте порядок вызовов и параметры. Для ref и out посмотрите значение внешней переменной до и после вызова. Для рекурсии выберите один кадр и не переносите в него параметры соседнего: одинаковое имя n не означает одну общую переменную.

Качественная проверка отражает контракт. Чистый метод вызывают повторно с одинаковыми аргументами и ожидают тот же результат. Try-метод испытывают на успехе и отказе, проверяя out. Метод с ref испытывают также на сохранении состояния при недопустимом входе. Вывод в TextWriter сравнивают целиком, включая перевод строки. Так тесты объясняют требуемое поведение и сохраняют смысл при разумном изменении реализации.

## 8. Самопроверка и подробные ответы

Сначала ответьте: почему обмен int-параметров не меняет внешние переменные? Чем out отличается от ref? Достаточно ли проверить false у Try-метода? Может ли перестановка округления изменить чек? Что является базой рекурсивной суммы цифр? Почему одинаковое значение 7 выбирает разные перегрузки?

Ответ 1. При обычной передаче int метод получает копии; присваивания меняют его локальные параметры. Для изменения внешних переменных требуется явно согласованный ref. Ответ 2. Ref передаёт уже инициализированную переменную для чтения и возможного изменения. Out передаёт место для результата, которое метод обязан назначить до возврата; прежнее значение не является входом. Ответ 3. Нет: false может сопровождаться неверным или старым out, поэтому проверяются оба результата согласно условию.

Ответ 4. Да. При subtotal=0.15 и скидке 0.015 сначала округлённая скидка 0.02 даёт итог 0.13, а позднее округление разности даёт 0.14. Ответ 5. Нулевой остаток возвращает 0; деление аргумента на 10 приводит к этой базе за ограниченное число вызовов. Ответ 6. Перегрузка выбирается по статическому типу аргумента: int и double различны даже при равном математическом значении. Хорошее объяснение связывает поведение с объявлением и местом вызова, а не только называет ключевое слово.
