# Ввод, условия и выбор действия

## 1. От известного значения к неизвестному вводу

Предварительно нужно понимать переменные, арифметику и типы из урока 01. Здесь данные перестают быть заранее известными литералами: программа получает строку, проверяет её и выбирает дальнейшее действие. К концу урока вы сможете объяснить каждый путь обработки, включая конец ввода, ошибочный формат и допустимое число за пределами предметного диапазона. Начните с [примера](examples/Program.cs), затем решайте [условия](TASKS.md); [разборы](SOLUTIONS.md) открывайте после собственного решения.

В задачах ввод обычно передаётся параметром `string? text`. Это позволяет проверить программу повторяемо, без ручного ввода с клавиатуры. Знак вопроса здесь обозначает, что вместо строки возможно значение `null`. Каркас методов остаётся предоставленным: вы пишете последовательность проверок и возвращаете результат. Когда научитесь писать методы в уроке 04, тот же расчёт можно будет вызвать из настоящей консольной оболочки.

Не начинайте задачу с десятка вложенных условий. Сначала перечислите возможные исходы обычными словами и установите их приоритет. Например: данных больше нет; строка не содержит целого; число отрицательно; количество принято. Такая последовательность сразу показывает, какие проверки должны выполняться раньше, а какие получают значение только после успешного разбора. Важно различать данные и сообщение о данных: текст `"12"` ещё не является целым числом 12.

## 2. ReadLine, пустота и конец потока

`Console.ReadLine()` читает следующую строку стандартного ввода без завершающего перевода строки. Если пользователь нажал Enter на пустой строке, результатом будет `""`. Если строк больше нет, возвращается `null`. Это разные состояния. При работе с перенаправленным файлом EOF наступает естественно; в интерактивном Windows-терминале конец ввода обычно задаётся сочетанием Ctrl+Z и Enter. Не нужно полагаться на конкретную клавиатуру в автоматической проверке.

Контракт возврата null при отсутствии следующей строки описан в [документации Microsoft](https://learn.microsoft.com/en-us/dotnet/api/system.console.readline?view=net-10.0). Пустой текст может означать ошибку формата, пустое значение поля или команду завершения — это решает условие конкретной задачи. EOF означает, что очередную строку получить не удалось. Повторять чтение после EOF без другого источника данных обычно бессмысленно.

Учебная оболочка одной попытки может выглядеть так:

```csharp
string? text = Console.ReadLine();
if (text is null)
{
    Console.WriteLine("Конец ввода");
}
else
{
    Console.WriteLine($"Прочитано: [{text}]");
}
```

Квадратные скобки в выводе помогают увидеть пустоту и окружающие пробелы. Для тестов передавайте null непосредственно в метод разбора. Такой тест проверяет политику EOF и не зависит от того, как организован терминал. Не превращайте null в пустую строку автоматически, если задача требует разные ответы: потерянное различие уже нельзя будет восстановить позже.

## 3. TryParse и два вида корректности

`int.TryParse(text, out int value)` возвращает bool: удалось ли прочитать представимое в int число. При успехе `value` содержит результат. Слово `out` здесь является частью готового API; устройство собственных выходных параметров изучим в уроке 04. Метод Parse при неверном формате выбрасывает исключение, а TryParse позволяет выразить обычный отказ через условие.

```csharp
string? text = " 42 ";
if (int.TryParse(text, out int value))
{
    if (value >= 0 && value <= 100)
        Console.WriteLine($"Принято: {value}");
    else
        Console.WriteLine("Вне диапазона");
}
else
{
    Console.WriteLine("Неверный формат");
}
```

Синтаксическая корректность и смысловая допустимость различаются. `"-3"` — корректное int, но может быть недопустимым количеством. `"3.5"` не подходит для целого ввода. Очень длинная последовательность цифр тоже не даст int: тип имеет конечный диапазон. Нельзя после false обращаться к выходному значению как к успешно прочитанному числу и по нему выбирать предметную ошибку.

В небольшом методе удобно сделать ранние возвраты: сначала EOF, затем ошибка разбора, затем ошибка диапазона, в конце успешный результат. В консольной программе вместо возвратов можно использовать явные ветви. Логика одна и та же; важно не допустить выполнения расчёта после уже обнаруженного отказа. Тестируйте каждый из исходов отдельно, а не только положительный пример.

## 4. Логика и порядок вычисления

Сравнения `==`, `!=`, `<`, `<=`, `>`, `>=` дают bool. Для равенства используется `==`, а один знак `=` означает присваивание. Операция `!` меняет логическое значение на противоположное. `&&` требует истинности обеих частей, `||` — хотя бы одной. Запись «a не меньше нижней границы и меньше верхней» превращается в `a >= lower && a < upper`.

У `&&` и `||` есть короткое замыкание. Для `&&` правая часть не вычисляется, если левая уже false. Для `||` правая часть не нужна, если слева true. Это используется не только ради скорости, но и для безопасности:

```csharp
int value = 12;
int divisor = 0;
bool divides = divisor != 0 && value % divisor == 0;
Console.WriteLine(divides);
```

Программа выводит False без деления на ноль. Если переставить части, опасная операция выполнится раньше защиты. Символы `&` и `|` тоже могут работать с bool, но вычисляют обе стороны; подменять ими `&&` и `||` в таком условии нельзя.

Скобки делают предметное правило заметным. Доступ активному пользователю с владельцем или пропуском записывается как `active && (owner || hasPass)`. Общая блокировка добавляется отдельным требованием `&& !blocked`. Без скобок пропуск может случайно превратиться в самостоятельное основание, обходящее активность. Полезный тест обязан проверять именно такое конфликтное сочетание: обычный активный пользователь с пропуском пройдёт и у ошибочного выражения.

## 5. If, else и конечный выбор

If выполняет тело только при true. Else выбирается при false и относится к ближайшему синтаксически доступному if без else. Отступы не определяют эту связь. Поэтому для вложенных проверок особенно полезны фигурные скобки. Даже если тело состоит из одной инструкции, скобки уменьшают вероятность ошибки при последующем добавлении строки.

Цепочка проверок задаёт приоритет. Если при остановленном заказе нужно возвращать `paused` независимо от адреса и оплаты, этот случай проверяется первым. Перестановка строк может изменить поведение, хотя набор сравнений останется тем же. Перед рефакторингом составьте таблицу сочетаний флагов; для трёх bool существуют всего восемь комбинаций, их нетрудно проверить полностью.

Switch удобен, когда один дискриминатор выбирает из конечного набора точных значений. Его не нужно насильно применять к любому сложному логическому правилу:

```csharp
int code = 1;
switch (code)
{
    case 0: Console.WriteLine("north"); break;
    case 1: Console.WriteLine("east"); break;
    default: Console.WriteLine("invalid"); break;
}
```

Внутри метода case может завершаться return. В консольном фрагменте break завершает switch, после которого программа продолжается. Default описывает остальные значения. Не следует нормализовать неизвестный код по модулю или менять регистр команды, если условие требует точного текста. Дополнительная «удобная» обработка может быть ошибкой протокола.

Короткий выбор одного из двух значений можно записать условным оператором: `condition ? whenTrue : whenFalse`. Например, `running ? "running" : "stopped"` возвращает строку по текущему флагу. Вычисляется только выбранная часть. Если ветви требуют нескольких действий или вложенные операторы мешают чтению, обычный if остаётся яснее.

## 6. Границы и формат числа

Интервал `[opening, closing)` включает левую границу и исключает правую. При совпадении границ он пуст. Такой договор удобен для соседних временных окон: момент закрытия одного окна может стать открытием следующего без двойного учёта. Если условие допускает переход через полночь, потребуется другая модель; в задачах урока это ограничение оговорено явно.

Ступенчатая цена требует отличать накопление от выбора единой ставки. Если первые десять единиц стоят по 2, а следующие по 3, двенадцать единиц стоят `10*2 + 2*3`, а не `12*3`. Для каждой ступени полезно проверить число непосредственно до порога, на пороге и сразу после него. Эти случаи обнаруживают неверные знаки сравнения и забытые предыдущие начисления.

Текстовый ввод дробей зависит от формата. В техническом протоколе часто требуется точка и InvariantCulture; в пользовательском интерфейсе может понадобиться явно выбранная культура. Параметр NumberStyles определяет, допустимы ли знак, окружающие пробелы, десятичный разделитель, группировка тысяч и экспонента. Имя флага является настройкой библиотечного метода; самостоятельно писать перечисления пока не требуется.

В калькуляторе этого урока разрешены только ведущий знак и десятичная точка. Нельзя бездумно выбрать NumberStyles.Number: он разрешает группировку, и строка с запятой может получить неожиданное числовое значение. Такую ошибку нужно проверять отрицательным примером, а не надеяться, что однажды её покажет пользователь. Подробнее о культурах и строковых правилах поговорим в уроке 05.

## 7. Отладка дерева решений

Для условной программы таблица путей часто полезнее длинного списка входов. Запишите для каждого теста, какие проверки он проходит и на какой должен остановиться. Если нужны статусы EOF, invalid, range и operation, сформируйте конфликтные входы: например, EOF вместе с неизвестной операцией. Это подтвердит приоритет, который один неверный параметр отдельно не показывает.

В отладчике поставьте точку останова перед первым if. Наблюдайте исходную строку, bool от разбора и разобранное число. После шага обязательно различайте «ветка пропущена» и «выполнена другая ветка». Отсутствие вывода иногда означает, что условие не было истинным, а иногда — что сообщение забыли во всех путях. Для возвращающего метода компилятор обнаруживает многие отсутствующие return; предметно неверный статус всё равно требует теста.

Чистота проверки важна для сравнения версий. Метод, принимающий строку и возвращающий статус, удобнее испытывать, чем метод, который одновременно просит пользователя ввести данные, меняет общие настройки и печатает ответ. Не обязательно разбираться в архитектуре приложения, чтобы уже сейчас сохранять это разделение. Готовый каркас создаёт такую возможность; ваша часть — сформулировать точный выбор для любых разрешённых входов.

## 8. Самопроверка и ответы

Ответьте до чтения объяснений: чем null отличается от `""`? Почему `TryParse("-3", ...)` может быть успешным при недопустимом количестве? Какое условие ставить первым в безопасной проверке делимости? Когда граница 10 должна попасть в первую тарифную ступень? Почему пропуск с неактивным пользователем — полезный тест доступа? Что меняет перестановка ранних возвратов?

Ответ 1. Null сообщает об отсутствии очередной строки, а пустая строка является реально прочитанной строкой нулевой длины. Их объединение допустимо только по явной договорённости. Ответ 2. TryParse проверяет представимость значения в типе, а смысловой диапазон количества проверяется отдельно. Ответ 3. Сначала проверяют ненулевой делитель; только затем справа от && вычисляют остаток.

Ответ 4. Если первые десять единиц имеют начальную цену, проверка первой ступени использует `units <= 10`. При этом цена следующих единиц добавляется к уже оплаченной базе. Ответ 5. Такой вход выявляет отсутствие нужных скобок: выражение с самостоятельным `|| hasPass` могло бы обойти активность. Ответ 6. Ранние возвраты определяют приоритет при одновременных проблемах. Переставлять их можно только после доказательства эквивалентности или сознательного изменения требований. Правильное объяснение называет конкретный конфликтный вход, а не только общую фразу о порядке условий.
