# Урок 15. Асинхронность, отмена и потоки данных

Нужны исключения, файлы и JSON, делегаты, LINQ и обобщения. После урока вы сможете написать метод, чей Task действительно представляет всю работу, передать отмену и проверить порядок без задержек. Для практики используются память, временные файлы и управляемые обещания. Сеть и внешние сервисы не нужны. Асинхронность рассматривается как договор о завершении операций и освобождении ожидающего потока во время I/O, а не как обязательное ускорение каждого алгоритма.

## 1. Task, async и await

`Task` представляет будущее завершение без отдельного результата, `Task<T>` — завершение с результатом типа T. Задача может быть ещё незавершённой, успешной, ошибочной или отменённой. Сам объект Task не равен потоку. Работа может завершиться синхронно, продолжиться после ожидания I/O или включать несколько других задач.

```csharp
static async Task<int> DoubleAsync(Task<int> input)
{
    int value = await input;
    return checked(value * 2);
}
```

Модификатор async разрешает await и даёт компилятору построить продолжение метода. Тело начинает выполняться при вызове. Если ожидаемая задача уже завершилась, выполнение может продолжиться сразу. На незавершённом await метод возвращает управление вызывающему вместе с Task, а оставшаяся часть выполняется после завершения зависимости.

Поэтому строка перед первым незавершённым await выполняется до возврата Task. Нельзя утверждать, что весь async-метод автоматически стартует позже или обязательно на другом потоке. Также async без реального ожидания не делает вычисление асинхронным: синхронный тяжёлый цикл остаётся синхронной работой.

Возвращаемый Task должен охватывать все обещанные действия: чтение, обработку, уведомление и необходимое освобождение. Если метод запускает save, но возвращает CompletedTask до его конца, вызывающий получает ложное сообщение о завершении. Именно такую ошибку проверяет задача с уведомлением после сохранения.

## 2. Почему не следует блокировать ожидание

`.Result` и `.Wait()` заставляют текущий поток ждать. В коде, который уже умеет работать асинхронно, обычно нужно await. Он сохраняет связь зависимостей, не занимая поток блокирующим ожиданием незавершённого I/O. В некоторых окружениях смешение блокировки и захвата контекста способно привести к взаимному ожиданию; для базового курса достаточно не создавать этот узел без необходимости.

Исправление ошибки типов через `Task.FromResult(input.Result * 2)` устраняет лишь несовпадение int и Task&lt;int&gt;, но оставляет блокировку. Обёртка Task.Run вокруг Result тоже не исправляет архитектуру ожидания: она переносит занятую ожидающую нить в пул. В упражнениях требование «вернуть незавершённый Task немедленно» проверяется управляемой незавершённой зависимостью.

Для файлов используйте настоящие асинхронные API: `ReadAllTextAsync`, `WriteAllTextAsync`, `ReadAsync`. Последовательность зависимых операций выражается последовательными await. Если чтение должно увидеть завершённую запись, оно начинается после await записи. Кодировка и владение файлом остаются важными независимо от асинхронности.

Поток не обязан поддерживать Length или Seek и не обязан заполнять весь буфер за один ReadAsync. Возвращённое число — фактически прочитанные байты, ноль сообщает EOF. Суммировать нужно именно эти числа. Использование памяти фиксированного буфера позволяет обрабатывать большой источник, не загружая его целиком.

## 3. Ошибки и жизненный цикл

Исключение async-операции сохраняется в её Task и наблюдается при await. `try/catch` должен охватывать не только запуск зависимости, но и ожидание её завершения. Если сохранить задачу внутри try, а await сделать снаружи, поздняя ошибка уже не попадёт в тот catch.

Вариант TryRead перехватывает только FormatException и возвращает флаг неуспеха. IOException и отмена означают другое и распространяются. Успешное чтение числа ноль остаётся `(true,0)`, поэтому результат не смешивается с ошибкой `(false,0)`. Тип и структура ответа помогают сохранить это различие.

У делегата-фабрики ошибка может возникнуть синхронно, прежде чем он вернул Task. Async-обёртка способна превратить её в faulted Task и сохранить общий протокол набора операций. Это важно, когда требуется запустить все фабрики, даже если одна сразу бросила исключение. Проверка всего массива зависимостей до первого запуска отдельно защищает от частичных действий при неверной конфигурации.

`async void` оставляют главным образом для обработчиков событий, чей внешний договор требует void. Для обычного метода возвращайте Task: вызывающему нужны ожидание и наблюдение ошибки. Игнорирование возвращённой задачи не является нейтральной записью — оно отделяет её жизненный цикл от вызывающего. Если такое поведение действительно нужно, политика обработки ошибок должна быть отдельной и явной.

## 4. Отмена является кооперативной

`CancellationTokenSource` управляет запросом отмены, а `CancellationToken` передаёт этот запрос операции. `Cancel()` не прерывает произвольный код насильно. Метод и его зависимости должны проверять токен либо передавать его API, которое это делает. Обычная проверка — `token.ThrowIfCancellationRequested()`.

Предварительная проверка гарантирует, что уже отменённая операция не начнёт запись или внешний callback. Передача того же токена зависимости сохраняет управление вызывающего. Проверка после await полезна, если зависимость могла проигнорировать отмену и вернуть успешное значение. Конкретные точки проверки задают наблюдаемое поведение, поэтому фиксируются в условиях задач.

Отмена не равна успешному пустому результату или ошибке формата. Не превращайте OperationCanceledException в ноль через широкий catch. Не повторяйте отменённую операцию без отдельного решения. Если отмена пришла между попытками retry, следующий круг должен заметить её до очередного запуска зависимости.

В ограниченном параллелизме токен может отменить ожидание слота, даже когда уже выполняющаяся work не принимает токен и продолжает работу. Это честное ограничение сигнатуры. Метод обязан дождаться всех созданных обёрток до освобождения общего semaphore. В реальном проекте по возможности передают отмену и самому I/O, но нельзя обещать остановку зависимости, которой этот механизм не предоставлен.

## 5. Независимые операции и предел параллелизма

Чтобы совместно ожидать независимые операции, сначала получают все их Task, затем используют `Task.WhenAll`. Если await стоит внутри цикла перед запуском следующей фабрики, операции становятся последовательными. WhenAll возвращает результаты в порядке входных задач, а не в порядке их завершения. Это легко проверить, завершив второй управляемый Task раньше первого.

`WhenAny` возвращает задачу-победителя. После первого await нужен ещё await самой выбранной задачи, чтобы получить её значение или ошибку. Успешное завершение внешнего WhenAny не означает успех внутреннего победителя. Проигравшие операции не отменяются автоматически и могут продолжаться. Их дальнейшее ожидание и ошибки остаются частью владения вызывающего.

Неограниченный запуск тысяч I/O-операций может превысить доступный ресурс. `SemaphoreSlim` задаёт максимальное количество одновременно незавершённых вызовов. Сначала await WaitAsync, затем try с ожидаемым work и finally с Release. Если Release стоит только после успешного результата, одна ошибка способна навсегда занять слот.

Не освобождайте слот, который не был захвачен: WaitAsync располагается до try/finally освобождения. После этого finally обслуживает любые пути выхода work. Сам semaphore уничтожается только после завершения всех созданных задач. В тестах закрытые gate занимают слоты, а отдельное обещание сообщает о запуске следующей работы. Так проверка не зависит от скорости компьютера.

## 6. Потоковая выдача и владение ресурсом

`IAsyncEnumerable<T>` представляет не один будущий массив, а последовательность элементов, каждый из которых может потребовать ожидания. Метод-итератор использует `async`, `yield return` и возвращает IAsyncEnumerable. Потребитель читает его через `await foreach`.

```csharp
await foreach (string line in NonBlankLinesAsync(reader, token))
    Console.WriteLine(line);
```

Тело итератора обычно начинает работу при продвижении перечислителя, поэтому и проверка null внутри может сработать при первом MoveNextAsync, а не при создании объекта последовательности. Атрибут `EnumeratorCancellation` у параметра токена позволяет согласовать отмену перечисления. В уроке он используется с явным параметром CancellationToken и проверкой перед чтением.

Потоковая обработка означает, что первый элемент может быть выдан до чтения всего источника. Если сначала ReadToEndAsync и затем Split, память и жизненный цикл уже другие. Ручной вызов MoveNextAsync в тесте позволяет получить первую строку, отменить токен и убедиться, что вторая ещё не прочитана.

Владение ресурсом также задаётся контрактом. Метод чтения чужого Stream не должен закрывать его, если поток принадлежит вызывающему. Если метод принимает владение `IAsyncDisposable`, `await using` гарантирует вызов и ожидание DisposeAsync на успехе, исключении и отмене. Возвращаемый Task не считается завершённым, пока асинхронное освобождение не закончилось. Ошибки самого освобождения требуют отдельной политики; в задачах тестовый ресурс освобождается успешно.

## 7. Повтор, импорт и детерминированные проверки

Retry нужен только для заранее определённого класса временных ошибок. В упражнении повторяется IOException, но не FormatException или отмена. Максимальное число попыток включает первый вызов. Последняя ошибка распространяется; между попытками снова проверяется токен. В производственном окружении часто нужны задержка, backoff и ограничения повторяемого действия, однако задача изолирует именно протокол, чтобы его можно было доказать.

Асинхронный импорт JSON сначала читает и проверяет весь снимок, затем выполняет последовательные save. Это предотвращает побочные эффекты от заранее неверной последней записи. Но если ошибка возникла уже внутри save второго элемента, первый мог сохраниться. Отсутствие автоматического отката является частью договора. Асинхронность не создаёт транзакцию.

Для проверок порядка используйте `TaskCompletionSource` с `RunContinuationsAsynchronously`. Закрытый gate представляет незавершённую операцию. До SetResult проверяйте, что внешний Task ещё не завершился и преждевременных callbacks нет. Затем откройте gate, await результат и проверьте завершённое состояние. SetException и отменённые Task покрывают другие пути.

Не используйте Task.Delay как доказательство: «не произошло за короткое время» не значит «не может произойти». Не проверяйте порядок по секундомеру. Завершайте все созданные тестовые обещания и ожидайте задачи, чтобы сценарий не оставлял фоновые хвосты. Отдельные ошибки прогоняйте на независимых зависимостях и счётчиках, иначе следы предыдущего теста будут смешиваться с текущим.

## 8. Самопроверка и развёрнутые ответы

Сначала объясните: когда стартует async-тело; почему нужен второй await после WhenAny; кто останавливает отменённую операцию; где Release; какое завершение обязан представлять Task сохранения.

Ответ 1. Тело начинает исполняться при вызове и идёт до первого незавершённого await. Если все ожидания уже готовы, метод может пройти почти целиком синхронно. Async описывает возможность приостановки, а не обязательный новый поток.

Ответ 2. Первый await возвращает саму завершившуюся задачу. Второй получает её результат и наблюдает исключение либо отмену. Без него можно ошибочно объявить успешной гонку, в которой победитель на самом деле упал.

Ответ 3. Отмена кооперативная: токен сообщает запрос, код и API решают, когда его заметить. Предварительная проверка предотвращает запуск, передача токена поддерживает отмену I/O, повторная проверка после ожидания уточняет политику результата. Сам Cancel не уничтожает поток исполнения.

Ответ 4. Release находится в finally после успешного WaitAsync. Он исполняется при любом выходе из work, а не только при return результата. Если слот не был захвачен, Release не нужен и может нарушить счётчик semaphore.

Ответ 5. Task должен охватывать само сохранение, положенное после него уведомление и принятое методом освобождение ресурсов. Ранний CompletedTask нарушает этот договор. Проверка закрытым gate делает нарушение наблюдаемым до завершения сохранения.

Официальная справка: [модель TAP с async и await](https://learn.microsoft.com/en-us/dotnet/csharp/asynchronous-programming/task-asynchronous-programming-model). Условия и решения разделены; в исполняемых проверках курса нет зависимости от сети, случайной скорости диска или реальных пользовательских данных.
